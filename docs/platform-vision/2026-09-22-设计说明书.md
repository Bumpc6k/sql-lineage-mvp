# 数据智能平台（DIP）· 设计说明书（开发交接版）

> 版本 v1.0 ｜ 2026-09-22 ｜ 配套：《项目规划与功能设计 v2》《功能点清单与工作分解》《协作与分工机制》《定稿原型 `sketches/200-chat-final/`》
>
> **这份文档解决一个问题**：开发者拿到原型截图之后，知道"每一屏由哪些组件拼成、每个组件什么状态、颜色取哪个令牌、点下去的时序是什么、先做哪块"。
> 原型是**视觉与交互的样本**，本说明书是**它的规格化描述**——两者冲突时，以本说明书为准（原型里为了省事写死的假数据除外）。

| 维度 | 结论 |
| --- | --- |
| 产品主张 | **对话即入口，回答必带凭证**。核心差异不是"AI 会聊天"，而是**可追溯** |

## 1. 设计目标与四条铁律

**四条铁律**（违反即视为缺陷，评审要打回）：

1. **无凭证不发布**：任何结论（数字/公式/表名）必须能点开溯源——血缘图 / 口径详情 / HTML 报告 / 实例日志，至少一个。
2. **不确定必须显式说**：`status ∈ verified / inferred / candidate / unresolved / stale`，界面上必须有可见标记，不允许"看起来很确定"。
3. **写操作必经三步**：生成草稿 → 人工审核 → 执行落地，且全程留痕；P1 只读，不做落地。
4. **降级要说得明白**：没有 LLM key 就进"规则模式"，界面顶部必须亮出模式与原因，且数据仍来自真实内核（不伪造）。

**设计目标**（衡量标准）：把"ads 表的这个字段怎么来的"从"翻 3 个脚本 + 问 2 个人"压到**一次提问 + 3 次点击**。

## 3. 核心屏 · 对话工作台交互规范

### 3.1 布局与栅格

```
┌ 顶栏 54px（产品名 · 模式徽标 · 内核状态 · 用户）────────────────┐
│导航 56px│ 会话列 228px │ 对话区 flex:1（最小 520px）│ 右面板 45%（最小 500px）│
└ 输入区（吸底）──────────────────────────────────────┘
```
- 断点：`<1280px` 右面板改为**抽屉**（点凭证滑出）；`<960px` 会话列收起为图标；`<768px` 单栏（移动端只读 + 提问）。
- 右面板宽度上限 720px：超过则留白，不拉伸（留白比超宽图好看）。

### 3.2 交互时序（一次提问 = 6 步）

| 步 | 界面行为 | 规格 |
| --- | --- | --- |
| 1 提问 | 输入框提交 → 用户消息右对齐进流 | 发送后**立即**插入"思考中"占位（骨架，不转圈超过 300ms 才显示） |
| 2 编排 | 顶部出现**工具步骤条**（这是 Agent 的"动作可视化"） | 默认折叠成一行：`查血缘 /analyze ✓ 0.4s · 检索口径 /kb/search ✓ 0.2s`；点开显示**真实请求 JSON + 返回摘要 + 耗时**（不许加密、不许美化） |
| 3 结论 | 结论卡淡入，数字/公式用等宽字体 | 徽标一排放：`status` + 置信度 + 版本 + 来源行；**status 不是 verified 时，卡片左描边换色并加一句"为什么不确定"** |
| 4 证据 | 结论下方列 1~3 张凭证卡 | 三型：血缘图（上游 N 张 · 可展开 M 张）、口径详情（版本 · 状态 · 分解项数）、HTML 报告（编号 · 体积）。**张数 0 时禁止发布该结论**（改为"我只能确定到这一步"+ 反问） |
| 5 联动 | 点结论卡/凭证卡 → 右面板切到对应 tab 并高亮来源标签 | 切 tab 不改变对话滚动位置；右面板头部 `证据 · 来源 /analyze（字段级血缘）` 跟随更新 |
| 6 追问 | 结论下方 2~3 个"建议追问"胶囊 | 由 Agent 依据未展开的证据生成（例：`改 output_qty 会砸哪些下游？`）；点击直接发送 |

### 3.3 元素级规格

| 元素 | 规格 |
| --- | --- |
| 状态徽标 | `verified` 绿 / `inferred` 蓝 / `candidate` 灰 / `unresolved` 橙 / `stale` 红灰。**颜色 + 文字同时出现**（不能只靠颜色） |
| 置信度 | 显示两位小数（`0.93`）；`<0.7` 必须在结论上方提示"建议人工确认" |
| 来源行 | 落盘到**文件 + 行号**（`ads/ads_产销存月报.sql 第 4 行`）或 `报告 rpt_xxx`；不允许只写"来自血缘服务" |
| 引用条（常驻） | 一行胶囊：表（带层次圆点）/ 命中口径 / 报告数 / 内核调用次数与耗时；点击即切面板 |
| 上下文 tab | 四段：引用的表 → 命中的口径 → 凭证清单 → 调用与审计。**只放"这一会话引用了什么"，不重复放结论** |
| 血缘图（小图） | 4 节点 3 边起步，列序 `ods→dwd→dws→ads`，**连线只允许左→右**，当前结论依赖链高亮；节点标题缩短为表名，`title` 悬停看全名 |
| 血缘图（大图） | 全链路 + 维表；右上角 `N 张表 / M 条边`；下游视图点"下游"切换 |
| 输入框 | `@` 表、`#` 口径、`/` 指令；`Enter` 发送、`Shift+Enter` 换行；禁用词表命中时提示"该问题需人工确认口径" |
| 降级条 | 规则模式时顶栏亮 `规则模式` 徽标 + 悬停说明原因（未配 key / 模型不可用），**不弹窗打断** |

### 3.4 验收点击路径（P1 唯一必须做到极顺的路径）

```
登录 → 首屏对话框 → 问「ads.ads_产销存月报 的产量怎么来的？」
→ 工具步骤条展开可见 /analyze 与 /kb/search 的真实返回
→ 结论：产量 = 打码量 + 跳码量 − 重码量（verified · 0.93 · v3 · 来源第 4 行）
→ 点「血缘图」凭证 → 右面板高亮产量依赖链（4 节点）
→ 点「口径详情」凭证 → 公式 + 依赖字段 + 版本 + 责任人 + 状态
→ 点「HTML 报告」凭证 → 报告卡 → 新窗口打开自包含报告
→ 点「上下文」tab → 引用的表 / 命中口径 / 凭证 / 调用与审计
→ 点左侧「血缘」→ 血缘中心全链路 + 表详情 + 影响分析
→ 全程在审计日志留下记录
```
**任何一步超过 1 次点击或出现空白屏，算未达标。**

**字号/间距**：正文 13~14px（对话正文 15px）、标签 11.5~12.5px、辅助 10~11px；间距用 4 的倍数（4/6/8/11/13/22）；圆角 8（控件）/ 9~11（卡片）/ 999（胶囊）；**等宽字体只用于标识符与公式**（表名、字段名、`/analyze`、公式）。

### 4.2 主题机制（深色不是"另做一套"）

- 一个 `data-theme="light" | "dark"` 挂在 `<html>` 上，**所有颜色只走令牌**，组件里禁止出现字面量色值（评审用 `grep '#[0-9a-fA-F]\{3,6\}' src/features` 即可检查）。
- 取值优先级：用户显式选择（持久化到 localStorage / 用户配置）> 跟随系统 `prefers-color-scheme` > 默认浅色。
- 顶栏提供切换按钮（☀/☾）；首帧要**先读偏好再渲染**，避免"白屏闪一下"（在 `index.html` 里内联 3 行脚本设 `data-theme`）。
- 深色下额外要求：**纯白不用**（用 `--fg` 的 `#e6e9ee`）、阴影改描边、报告 iframe 加浅色遮罩提示"报告为浅色"，避免深底夹白页刺眼。
- 原型已实现：定稿原型右上角可切换，也支持 `?theme=dark` 直达（见 §10 附截图）。

### 4.3 无障碍底线（不做可访问性加分，但**这三条必须**）

1. 正文对比度 ≥ 4.5:1（**已实测**：浅色 17.8 / 10.3 / 6.0 / 4.7，深色 13.9 / 10.9 / 6.6 / 5.5，见下表；令牌值按实测调过两轮：浅色 `--dim2` 由 `#8b94a3` 改 `#6b7482`、`--ok` 由 `#0f9960` 改 `#0b7a4d`）。
   **判定口径**：徽标/高亮的**边框**属装饰性（语义由同行的文字承载，见规则 2），按 WCAG 1.4.11 不要求 3:1；若有元素仅靠边框区分状态，必须补文字或图标。
2. 状态不能只用颜色表达（徽标=色块+文字；高亮节点=色+描边）。
3. 全键盘可达：`Tab` 能走到凭证卡与 tab，`Enter` 能触发；焦点环用 `--ring` 且不被裁掉。

## 7. 交互优化清单（开发阶段必做，按优先级）

| P | 优化项 | 说明 |

| P0 | 流式输出 | 结论逐字出（SSE），步骤条与正文并行推进，避免"等 8 秒白屏" |

## 8. 前后端接口形状（与统一结果模型对齐）

一次问答，`portal-api` 返回的**回答对象**（前端渲染的唯一数据源）：

```json
{
  "answer_id": "ans_01H...",
  "text": "产量 = 打码量 + 跳码量 − 重码量，字段级依赖 cdw.dws_产销存汇总.output_qty。",
  "value": { "type": "formula", "expr": "打码量 + 跳码量 − 重码量" },
  "status": "verified",
  "confidence": 0.93,
  "source": { "kind": "sql_line", "file": "ads/ads_产销存月报.sql", "line": 4 },
  "version": "v3",
  "evidence": [
    { "type": "lineage", "ref": "graph:ads.ads_产销存月报", "summary": "上游 3 张 · 可展开 14 张 / 3 层" },
    { "type": "metric",  "ref": "metric:产量@v3",            "summary": "v3 · verified · 分解 3 项" },
    { "type": "report",  "ref": "report:rpt_20260922_a1b2c3d4","summary": "HTML · 182 KB" }
  ],
  "suggestions": ["dws 层的产量口径是什么？", "改 output_qty 会砸哪些下游？"],
  "tool_calls": [
    { "name": "lineage.analyze", "args": {"sql": "...", "dialect": "hive"}, "ms": 412, "ok": true },
    { "name": "kb.search", "args": {"keyword": "产量"}, "ms": 187, "ok": true }
  ],
  "mode": "rule",
  "audit_id": "aud_01H..."
}
```
- **前端不得自行推断 status/confidence**；缺失字段按 `unresolved` 渲染并显示"证据不足"。
- `evidence` 为空数组时，前端**必须**渲染"未找到凭证"提示且不展示结论数字（铁律 1）。
- 工具调用契约走旧内核 HTTP：`POST /analyze`、`POST /kb/search`、`POST /impact`、`GET /report/{id}`（详见新仓库 `integrations/lineage-client`）。

## 9. 模块开发顺序（按含金量排序）

> 原则：**先把"别人替代不了"的做出来**——对话编排、证据装配、口径固化是产品的含金量；登录壳、设置页只要有。

| 批次 | 模块 / 工作项 | 为什么这个顺序（含金量） | 依赖 |
| --- | --- | --- | --- |
| **B1 骨架** | `portal-api` 骨架 + `lineage-client` 契约客户端（W-101/W-105/W-106/W-110） | 没有稳定契约客户端，后面全是返工；含金量中，但是**一切的地基** | 旧内核 17 端点契约 |
| **B2 心脏** | **对话编排（意图→工具路由）+ Agent 回答装配（统一结果模型）**（W-114/W-118/W-121） | ⭐**最高含金量**：这一块决定"可追溯"能不能成立，也是和 ChatBI 的分界线 | B1 |
| **B3 取证** | 证据装配（血缘/口径/报告三类证据组装）+ 审计落库（W-123/W-129/W-141） | ⭐高：铁律 1 的落地；审计是 B 端信任来源 | B2 |
| **B4 呈现** | 对话工作台前端（消息流 / 步骤条 / 凭证卡 / 右面板 / 引用条）+ 血缘中心（W-131/W-135/W-137） | 高：把前两批的能力"看得见"；血缘图渲染是门面 | B2 |
| **B5 补齐** | 口径库 / 报告中心 / 审计页 / 系统设置 / 登录（W-145/W-149/W-153/W-157） | 中：锦上添花，可并行认领 | B1 |
| **B6 打磨** | §7 交互优化 P0 项 + 深色主题 + 空/错/降级态全覆盖（W-161~） | 中：决定"像不像成品" | B4 |

**推荐人手**：B2 由对业务口径最熟的人带（他同时是口径数据的责任人），B4 由前端独立认领并行做；B1 必须先合并，B2/B4 才能在契约上并行。
