0. 一页纸结论

问题结论
方向对不对对，而且是升级。原来的编排（意图判定→工具计划→证据装配→答案成型）写死在代码里；改成"harness 底座 + 万物皆 skill"后，加一种能力 = 加一个 skill，不用改编排内核
最大的变化从「规则优先、LLM 兜底」改成 「LLM/决策模型为主」。这是一次根本性立场切换，收益是能力上限高，代价是不确定性变高（会编、会漂、可能幻觉出 truncate table）
因此必须补硬的三处① 事实不得由模型生成——要用机制保证（执行器回执校验），不能靠提示词；② 防火墙 fail-closed（拿不准就拒），且中高风险要留痕 + 复核；③ 知识回写也是一种写操作，必须过审、有版本、可回滚，否则知识库会被幻觉污染
原设计里缺的一层智能防火墙（你提的）。我原方案只有"写操作必经生成→审核→执行"的原则，没有独立的策略引擎——这是真正的缺口，补上后整条链路才闭环
可复用的已有资产知识库（75 口径 / 298 字段 / 139 术语 / 76 规则）、SQL 血缘解析、生成四层（SQL→链路→落地→反向校验）、海豚插件（执行器雏形）、继承下来的编排骨架（可改造成 skill 注册表）

2. 必须补硬的三处（按风险排序）

2.1 事实不得由模型生成 —— 要用机制，不能靠提示词

LLM 为主之后，最大的风险不是"答得不好"，而是答得很像真的。原设计有一条铁律"事实来自内核"，那是在规则模式下天然成立的；换成 LLM 主导后，必须换成机制：

  • 执行器回执校验：skill 返回必须带结构化回执（source/endpoint/ms/rows/affected），harness 只允许用回执里的数字与标识符组答案；模型输出里出现回执之外的表名/数字/字段名，一律标红或打回重写。
  • 引用强制：每条结论必须挂 evidence[]（证据 id），无证据的结论不允许输出（沿用现有 Answer 模型校验，铁律 1 继续生效）。
  • 敏感动作白名单：模型只能"提出"动作，不能"决定"动作——动作由防火墙裁决（见 2.2）。

    • 2.2 智能防火墙：fail-closed、分级、留痕、可复核

    建议做成独立组件（而不是散在 skill 里的 if-else），判定顺序为：身份 → 权限 → 风险分级 → 处置。

    级别例子处置
    L0 只读查血缘、检索口径、看集群状态、select直接通过（仍留痕）
    L1 低风险写生成 SQL 草稿、生成调度流程草稿、写临时表通过 + 强制附"未执行"标注
    L2 中风险建表、改表结构、上线调度流程、重跑历史实例回给用户确认（展示影响面：下游 N 张表 / M 个任务）
    L3 高风险补数超大范围、删除分区、修改生产口径、批量重跑双人复核（提交人 + 负责人），带时效令牌
    L4 禁止drop table、truncate、无 where 的 delete/update、跨域导出直接拒绝并解释原因，记录尝试

    要点：① 拿不准按上一级处理（fail-closed）；② 每次判定都要落审计（谁、什么动作、判定依据、结果）；③ 审批令牌一次性、有时效、绑定具体动作，不能复用。

    2.3 知识回写 = 写操作，同样要过审

    "有价值的知识，用户确认后落盘"这个闭环很好，但知识库是下游所有回答的地基——被幻觉污染一次，后面所有回答都会错。建议：

  • 回写走候选池（candidate 状态），不直接进正式口径；
  • 需要责任人审核（谁的表谁审）+ 去重/冲突检测（同字段两条口径公式不同 → 必须仲裁，不允许并存）；
  • 版本化 + 可回滚（每条口径有版本号与来源脚本，能一键回退）；
  • 回写内容必须带来源证据（脚本 + 行号 + 摘要），无来源不允许入库。

    3. Skill 契约（最小字段集，供敲定）

    一个 skill 想被 harness 调用，至少要声明：

    字段说明例子
    name / version唯一名 + 版本lineage.analyze@1
    when什么时候用（给决策模型看的描述）"用户给了 SQL 或问某脚本的血缘"
    input_schema / output_schema入参出参 JSON Schema（供模型填参数 + 供校验）{sql, dialect, depth}
    side_effectnone / read / write / ddl / dml决定防火墙最低级别
    auth_scope需要的权限点lineage:read、schedule:write
    idempotent / timeout / retry幂等性、超时、重试语义幂等 + 30s + 仅连接类错误重试
    evidence_kind返回值能作为哪类证据lineage / metric / report / plan
    renderer结果用哪个视图渲染table / graph / sql / diff
    budget单次会话内的调用上限（防循环）最多 6 次

    调度可控性是这类架构最容易踩的坑：必须限制「单轮最大 skill 数」「同 skill 最大重试」「总 token/时间预算」，否则模型会绕圈。

    4. 执行器协议（建议的最小方法集）

    SchedulerAdapter（调度适配器，一个平台一个实现）
  list_workflows(project) / get_workflow(id)
  create_draft(pipeline) / validate(draft)          # 只产出草稿，不落地
  release(id) / offline(id)                          # L2 起，需审批令牌
  run(id, params) / rerun(instance_id)               # L2/L3
  get_instance_status(id) / fetch_logs(instance_id)
  list_instances(workflow, timerange)                # 补数范围评估用

MonitorAdapter（监控适配器）
  cluster_health() / queue_status()
  db_status(db) / table_stats(table) / slow_queries(top_n)
  lineage_graph(scope)                               # 已有：血缘图谱

    要点：新增一个调度平台 = 新增一个适配器，上游（harness/防火墙/skill）零改动——这正是你说的解耦，落点就在这两个协议上。

    5. 主流程（与图对应）

    用户指令
  → Harness（会话上下文 + 决策模型：意图 → 选 skill → 组参）
  → 【智能防火墙】身份/权限/风险分级
        ├─ L0/L1 → 执行器 → 回执 → 模型汇总 → 前端渲染（按 renderer）
        ├─ L2    → 回用户确认（附影响面）→ 带令牌 → 执行器 → 回执 → …
        ├─ L3    → 双人复核 → 带时效令牌 → 执行器 → …
        └─ L4    → 拒绝（解释原因 + 留痕）
  → 输出到对话框
  → 有价值的业务知识 → 用户确认 → 候选池 → 责任人审核 → 知识库（带版本/来源）
  → 查询/调度结果 → 由 renderer（格式化 skill）规范化展示（依赖图 / 结果表 / SQL / 执行计划）
  → 全链路审计（问题、skill 调用、判定依据、回执、确认人）
二次查询：Harness → 防火墙 → 知识库（优先本地知识，命中即不再打扰模型）→ 重复
初始化（可选，一次性）：调度器已有任务 → 批量解析 → 报告 + 候选知识（默认不落库）→ 人工抽检 → 入库

    6. 待敲定（10 条，附我的建议）

    #问题我的建议
    1LLM 为主后，"无 key 也能跑"还要不要保留？保留降级模式（只读能力走规则），但默认走模型；降级时界面必须显式标注
    2事实校验放在哪一层？harness 出口统一校验（回执白名单），不在每个 skill 里各做一遍
    3防火墙是独立服务还是进程内模块？P1 进程内模块 + 策略表（够用、好测）；多租户/多环境后再独立部署
    4L2/L3 的"确认人"是谁？L2：提问本人；L3：表责任人（知识库里已有责任人字段）+ 提问人，双人
    5审批令牌怎么防复用？一次性 + 绑定动作指纹（表名+语句 hash）+ 5 分钟时效
    6知识回写的审核链？候选池 → 责任人审核 → 入库（版本化），不允许模型直接写正式口径
    7会话记忆与知识库边界？会话记忆=临时（会话内）；知识库=长期（跨会话、需审核）。不把会话内容自动灌进知识库
    8多环境（开发/测试/生产）怎么隔离？连接与权限按环境分档，生产默认只读；跨环境动作视为 L3
    9前端结果渲染怎么可插拔？skill 声明 renderer，前端按名注册视图组件（先做 table/graph/sql/diff 四种）
    10初始化批量解析的范围？先做一个项目、只出报告不落库，人工抽检后再全量；落库走候选池

    8. 决策已定（2026-09-25 用户逐条确认）

    #问题决定落地影响
    1是否保留"无模型降级"不保留（暂时）无决策模型 = 平台不可用：必须明确报错 + 留痕，不能静默失败；测试用 mock 模型
    2事实校验放哪harness 出口统一校验（回执白名单）不在每个 skill 里各做一遍；只允许用回执中的数字/标识符组答案
    3防火墙形态独立部署的服务服务间签名调用；策略与判定可单独扩容与审计
    4审批复杂度只保留最高档需审批 + 上一级确认，暂不做审批模块风险判定简化为三档：自动通过 / 需上级审批 / 禁止
    5令牌机制一次性 + 绑动作指纹 + 5 分钟时效复用他人令牌不可行
    6知识回写审核链候选池 → 责任人审核 → 版本化入库禁止模型直写正式口径；冲突必须仲裁
    7会话记忆 vs 知识库会话记忆临时；知识库长期且需审核不把会话内容自动灌进知识库
    8跨环境动作视为"需审批"档，本人确认一次跨环境不再单独分级，与生产写同档
    9前端渲染可插拔按 skill 声明的 renderer 注册视图先做 table / graph / sql / diff 四种
    10初始化批量解析先一个项目 + 只出报告不落库 + 人工抽检合格后才走候选池入库
