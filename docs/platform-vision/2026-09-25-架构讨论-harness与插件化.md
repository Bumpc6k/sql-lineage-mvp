## 2. 必须补硬的三处（按风险排序）

### 2.1 事实不得由模型生成 —— 要用机制，不能靠提示词

LLM 为主之后，最大的风险不是"答得不好"，而是**答得很像真的**。原设计有一条铁律"事实来自内核"，那是在规则模式下天然成立的；换成 LLM 主导后，必须换成**机制**：

- **执行器回执校验**：skill 返回必须带结构化回执（`source/endpoint/ms/rows/affected`），harness 只允许用回执里的数字与标识符组答案；模型输出里出现回执之外的**表名/数字/字段名**，一律标红或打回重写。
- **引用强制**：每条结论必须挂 `evidence[]`（证据 id），无证据的结论**不允许**输出（沿用现有 `Answer` 模型校验，铁律 1 继续生效）。
- **敏感动作白名单**：模型只能"提出"动作，不能"决定"动作——动作由防火墙裁决（见 2.2）。

### 2.2 智能防火墙：fail-closed、分级、留痕、可复核

建议做成**独立组件**（而不是散在 skill 里的 if-else），判定顺序为：**身份 → 权限 → 风险分级 → 处置**。

| 级别 | 例子 | 处置 |
| --- | --- | --- |
| **L0 只读** | 查血缘、检索口径、看集群状态、`select` | 直接通过（仍留痕） |
| **L1 低风险写** | 生成 SQL 草稿、生成调度流程草稿、写临时表 | 通过 + 强制附"未执行"标注 |
| **L2 中风险** | 建表、改表结构、上线调度流程、重跑历史实例 | **回给用户确认**（展示影响面：下游 N 张表 / M 个任务） |
| **L3 高风险** | 补数超大范围、删除分区、修改生产口径、批量重跑 | **双人复核**（提交人 + 负责人），带时效令牌 |
| **L4 禁止** | `drop table`、`truncate`、无 `where` 的 `delete/update`、跨域导出 | **直接拒绝**并解释原因，记录尝试 |

要点：① **拿不准按上一级处理**（fail-closed）；② 每次判定都要落审计（谁、什么动作、判定依据、结果）；③ 审批令牌**一次性、有时效、绑定具体动作**，不能复用。

### 2.3 知识回写 = 写操作，同样要过审

"有价值的知识，用户确认后落盘"这个闭环很好，但**知识库是下游所有回答的地基**——被幻觉污染一次，后面所有回答都会错。建议：

- 回写走**候选池**（`candidate` 状态），不直接进正式口径；
- 需要**责任人审核**（谁的表谁审）+ **去重/冲突检测**（同字段两条口径公式不同 → 必须仲裁，不允许并存）；
- **版本化 + 可回滚**（每条口径有版本号与来源脚本，能一键回退）；
- 回写内容**必须带来源证据**（脚本 + 行号 + 摘要），无来源不允许入库。

## 3. Skill 契约（最小字段集，供敲定）

一个 skill 想被 harness 调用，至少要声明：

| 字段 | 说明 | 例子 |
| --- | --- | --- |
| `name` / `version` | 唯一名 + 版本 | `lineage.analyze@1` |
| `when` | 什么时候用（给决策模型看的描述） | "用户给了 SQL 或问某脚本的血缘" |
| `input_schema` / `output_schema` | 入参出参 JSON Schema（供模型填参数 + 供校验） | `{sql, dialect, depth}` |
| `side_effect` | `none` / `read` / `write` / `ddl` / `dml` | 决定防火墙最低级别 |
| `auth_scope` | 需要的权限点 | `lineage:read`、`schedule:write` |
| `idempotent` / `timeout` / `retry` | 幂等性、超时、重试语义 | 幂等 + 30s + 仅连接类错误重试 |
| `evidence_kind` | 返回值能作为哪类证据 | `lineage` / `metric` / `report` / `plan` |
| `renderer` | 结果用哪个视图渲染 | `table` / `graph` / `sql` / `diff` |
| `budget` | 单次会话内的调用上限（防循环） | 最多 6 次 |

**调度可控性**是这类架构最容易踩的坑：必须限制「单轮最大 skill 数」「同 skill 最大重试」「总 token/时间预算」，否则模型会绕圈。

## 4. 执行器协议（建议的最小方法集）

```
SchedulerAdapter（调度适配器，一个平台一个实现）
  list_workflows(project) / get_workflow(id)
  create_draft(pipeline) / validate(draft)          # 只产出草稿，不落地
  release(id) / offline(id)                          # L2 起，需审批令牌
  run(id, params) / rerun(instance_id)               # L2/L3
  get_instance_status(id) / fetch_logs(instance_id)
  list_instances(workflow, timerange)                # 补数范围评估用

MonitorAdapter（监控适配器）
  cluster_health() / queue_status()
  db_status(db) / table_stats(table) / slow_queries(top_n)
  lineage_graph(scope)                               # 已有：血缘图谱
```
要点：**新增一个调度平台 = 新增一个适配器**，上游（harness/防火墙/skill）零改动——这正是你说的解耦，落点就在这两个协议上。

## 5. 主流程（与图对应）

```
用户指令
  → Harness（会话上下文 + 决策模型：意图 → 选 skill → 组参）
  → 【智能防火墙】身份/权限/风险分级
        ├─ L0/L1 → 执行器 → 回执 → 模型汇总 → 前端渲染（按 renderer）
        ├─ L2    → 回用户确认（附影响面）→ 带令牌 → 执行器 → 回执 → …
        ├─ L3    → 双人复核 → 带时效令牌 → 执行器 → …
        └─ L4    → 拒绝（解释原因 + 留痕）
  → 输出到对话框
  → 有价值的业务知识 → 用户确认 → 候选池 → 责任人审核 → 知识库（带版本/来源）
  → 查询/调度结果 → 由 renderer（格式化 skill）规范化展示（依赖图 / 结果表 / SQL / 执行计划）
  → 全链路审计（问题、skill 调用、判定依据、回执、确认人）
二次查询：Harness → 防火墙 → 知识库（优先本地知识，命中即不再打扰模型）→ 重复
初始化（可选，一次性）：调度器已有任务 → 批量解析 → 报告 + 候选知识（默认不落库）→ 人工抽检 → 入库
```

## 9. 技术选型与契约（2026-09-25 已定）

### 9.1 Skill 契约（四条原则，用户已确认）

1. **声明与实现分开**：声明文件（YAML）+ 代码实现；加一个 skill = 加一个目录，**不改 harness 一行代码**。
2. **一个 skill = 一个动作**：流程编排留在 harness；确需组合的能力显式标 `composite: true`，不许把编排藏进 skill。
3. **skill 只申报风险，防火墙最终裁决**：即使有人把 `drop table` 声明成只读，也按策略表拒绝——**安全不靠自觉**。
4. **新增 skill 必须走 PR + 契约校验**：缺字段、声明与实现不符 → 门禁红，不许合并。

字段集见 §3。两条安全细节同批确认：**要执行的 SQL 必须由生成类 skill 产出并先过校验**（生成与执行分离）；**每个 skill 返回必须带回执**（来源端点/耗时/影响行数），供 harness 出口校验。

### 9.2 选型

| # | 选型 | 决定 | 备注 / 风险 |
| --- | --- | --- | --- |
| A | 决策模型 | **DeepSeek API**（先走 API） | 业余开发、暂无正式环境；统一走 **OpenAI 兼容协议 + 薄模型网关**（换模型/限流/记账不改业务） |
| B | harness 底座 | **采用 DeepSeek Harness（`dsh`）** | MIT ｜ TypeScript + Cordis 插件框架 ｜ 官方定位 "Everything is a Plugin" ｜ **v0.1 开发者预览版（2026-08 开源）** |
| C | skill 暴露 | **MCP** | skill 声明叠加在 MCP 之上：**MCP 管"怎么调"，契约管"能不能调、怎么展示"** |

**采用 dsh 的边界（必须守住）**：防火墙、出口事实校验、审计落库这三件留在**自有侧**，不塞进 dsh。
**风险与对策**：dsh 处于预览期、API 可能破坏性变更 → ① 锁定版本，不追 latest；② skill 契约锁在 **MCP** 层，外壳可替换而 skill 资产不动。

### 9.3 知识库：双通道（用户已确认）

| 通道 | 存什么 | 技术 | 角色边界 |
| --- | --- | --- | --- |
| **① 结构化通道（核心）** | 口径/公式、表、字段、术语、规则、血缘 | 既有知识库 + **实体锚定 + 精确匹配优先 + 强制来源**（脚本 + 行号） | **唯一允许产出结论数字的通道** |
| **② 文档通道（补充）** | 脚本注释、需求文档、SOP、会议纪要 | **WeKnora**（腾讯开源，MIT，v0.8.0：BM25 + 向量 + 重排 + GraphRAG；官方 MCP server 29 工具） | 只提供背景说明，**不产出结论** |

**为什么不能只靠文档 RAG**：v1 实测——一次检索返回 72 条命中，若不按"表名/字段名实体"过滤，会把「产量怎么来的」答成"上游透传"（错的），因为真实公式在 dwd 层而非 ads 层。

**知识提炼流水线**（唯一没做完的一段）：
```
脚本/任务流 → 解析血缘 → LLM 初筛候选口径 → 规则校验（必须有公式 + 依赖字段 + 来源脚本）
→ 候选池 → 责任人审核 → 版本化入库（可回滚）
```
