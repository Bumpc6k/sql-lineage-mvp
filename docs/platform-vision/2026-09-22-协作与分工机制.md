# 多人协作机制（怎么让多个开发者参与进来）

配套：《项目规划与功能设计 v1.1》《功能点清单与工作分解》 ｜ 2026-09-22

> 目标：**多人并行不打架**。打架的根因只有三种：① 契约没先定；② 边界没写死；③ 验收没标准。这份文档就是针对这三件事的规则。

---

## 1. 五条并行原则（先理解再动手）

| 原则 | 具体做法 | 违反的后果 |
| --- | --- | --- |
| **① 契约先行** | 任何跨模块交互先改 `packages/dip-contracts` 并生成 openapi/TS 类型，**契约 PR 合了别人才能动** | 后端改字段前端不知道，联调期互相等 |
| **② 边界写死并由工具强制** | `tools/check_layering.py`：越界 import 直接让测试失败（前端同理：业务代码不许直接 import 第三方对话库，只能走 `adapters/`） | 三个月后没人知道哪层能依赖哪层 |
| **③ 模拟数据先行（mock first）** | 前端不等后端：按契约先写 mock（`/mocks/*.json` + MSW 或本地 json server），后端按同一契约实现 | 前端干等，联调最后爆炸 |
| **④ 独立单元、独立验收** | 每个部署单元（web / api / adapter）都能单独起、单独跑门禁 | 必须全栈起来才能验证任何东西 |
| **⑤ 交付物的判定标准是"用户能用"** | 界面类工作项必须附**截图/录屏**，不接受"接口通了"当完成 | 出现"侧边栏能看见但一点就空白"这类返工 |

## 2. 仓库与分支策略

- **主干保护**：`main` 只接受 PR；禁止直推；合并前 CI 四项必须绿（lint / 单测 / 契约漂移 / 前端构建）
- **分支命名**：`feat/W-123-chat-home`、`fix/…`、`docs/…`、`chore/…`（**带上工作项编号**，评审时能一键跳回 Issue）
- **小步提交**：单个 PR ≤ 400 行改动（UI 与生成物除外）；宁可多开 PR，也不要一个 PR 改 20 个文件
- **提交信息**：`<type>(<scope>): <中文简述>`，例如 `feat(chat): 对话首屏接真内核（W-123）`
- **版本**：Tag 按阶段打（`p1.0`、`p1.1`…）；契约破坏性变更必须升 `/v2` 并写 ADR
- **两个仓库的关系**：内核仓库（`sql-lineage-mvp`）与平台仓库互不 import 内部模块；跨仓库改动必须**两边各一个 PR**，并在两边 PR 描述里互相链接

## 3. 工作流（从认领到合并）

```
①认领 Issue（GitHub Issues/Projects，按 Phase 与角色打标签）
     ↓  Issue 模板要求写清：交付物 / 验收方式 / 依赖 / 影响面
②改契约（如涉及跨模块）→ 契约 PR（≤1 天）→ 至少 2 人 approve 后合并
     ↓
③开功能分支，按 mock 先行的顺序写代码
     ↓  本地跑：make lint && make test && make gate-fast
④提 PR：填 PR 模板（改了什么 / 怎么验的 / 截图或输出 / 影响面 / 回滚方式）
     ↓  评审清单（见 §4）
⑤CI 四项全绿 + ≥1 人 approve → squash 合并 → 删除分支
     ↓
⑥在工作项里回填"验收证据"（截图/命令输出），把 Issue 关掉
```

**Issue 模板**（`.github/ISSUE_TEMPLATE/workitem.md`）：

```markdown
### 工作项：<ID 与名称>
**交付物**：一句话，可交付的东西（文件/页面/接口/脚本）
**验收方式**：可执行的命令，或可复现的点击路径（不接受"看起来没问题"）
**依赖**：W-xxx / 外部平台 / 数据
**影响面**：影响哪些模块、是否需要改契约、是否影响已有数据
**建议角色**：FE / BE / KB / OPS ｜ **规模**：S/M/L/XL
```

**PR 模板**（`.github/pull_request_template.md`）：

```markdown
### 关联工作项
Closes #<issue>（W-xxx）
### 改了什么
- 一句话一条，别贴 diff
### 怎么验证的（必须可复现）
- 命令 / 点击路径 / 截图（界面类必附截图）
### 契约与数据
- [ ] 改了契约（已同步 openapi.yaml + 前端 TS 类型 + 记录 ADR）
- [ ] 有无破坏性变更（有则说明 /v2 计划）
- [ ] 涉及数据迁移（附迁移与回滚脚本）
### 降级与错误态
- [ ] 依赖不可用时的表现已覆盖（无 LLM key / 内核挂 / 无权限）
### 回滚方式
- 怎么退回上一个可用状态
```

## 4. 评审清单（评审人照着问）

| 维度 | 要问的问题 |
| --- | --- |
| 边界 | 有没有跨层 import？有没有把平台特有名词写进公共层？ |
| 契约 | 响应字段有无新增/变更？前端 TS 类型同步了吗？ |
| 证据 | 界面类有截图吗？后端有真实调用输出吗？（**"接口通了"不算**） |
| 降级 | 内核挂了/没配 key/没权限，界面会怎样？ |
| 安全 | 凭据是否只存密文？日志/前端有没有泄露内部地址或 token？ |
| 审计 | 写操作与敏感读操作落审计了吗？ |
| 可测 | 新增逻辑有测试吗？（前端至少一个组件测试或可复现验收脚本） |
| 文档 | README/规划/ADR 需要更新的更新了吗？ |

## 5. 角色与 Owner 矩阵（CODEOWNERS 建议）

| 模块 / 目录 | Owner（默认评审人） | 说明 |
| --- | --- | --- |
| `packages/dip-contracts/**`、`contracts/**` | **全员会签**（至少 2 人） | 契约是并行的地基，改动代价最高 |
| `packages/dip-core/**` | BE-1 | 领域模型（无框架依赖） |
| `packages/dip-agent/**` | BE-2 | Agent 编排与降级策略 |
| `integrations/lineage-client/**` | KB | 与旧内核的唯一接口 |
| `apps/portal-api/**` | BE-1 / BE-2 | 身份、会话、审计、工具链 |
| `apps/portal-web/src/features/chat/**` | FE-1 | 对话与凭证（产品主线，优先级最高） |
| `apps/portal-web/src/features/lineage|metrics|reports/**` | FE-2 | 三个功能域页面 |
| `ops/**`、`.github/workflows/**` | OPS | 环境、CI、门禁、演示固化 |
| `docs/**` | 全员 | ADR 由提出变更的人写 |

> 人数少时无所谓"专属 Owner"，但**契约与 ops 必须双人**：这两处出错会让所有人一起返工。

## 6. 环境：让新人 10 分钟能跑起来

```bash
# 目标体验（新仓库 README 第一条）
git clone <repo> && cd data-intelligence-platform
make dev          # 起 postgres + portal-api + portal-web；灌种子数据；打印访问地址
make demo         # 一键走通「登录 → 对话 → 凭证 → 血缘图/口径/报告」并截图
make gate-fast    # lint + 单测 + 分层守卫 + 契约漂移（不需要旧内核）
make gate         # 上面 + 真调旧内核的端到端
```

**硬要求**：
1. **无 LLM key 也能跑**（规则模式），否则每个新人都要先申请凭据
2. **种子数据自带**一个能答得上来的示例（`ads.ads_产销存月报` 的产量），这样对话首屏一打开就有内容
3. 旧内核默认可不启动（`make gate-fast` 不依赖它），仅在需要端到端时才要求拉起

## 7. 沟通与节奏

| 节奏 | 内容 | 产出 |
| --- | --- | --- |
| **每日**（异步） | 每人一条：昨天做了什么 / 今天做什么 / 被什么挡住 | 挡住别人的**立刻升级**，不闷着 |
| **每周一次 30 分钟** | 看板过一遍（进行中/待验收/阻塞）+ 契约变更预告 | 下周工作项认领 |
| **每阶段结束** | **演示**（按规划里的验收路径现场跑一遍）+ 复盘 | 录屏归档 + P+1 工作项清单 |
| **契约变更时** | 发起人在群里发"契约变更预告"（改什么/谁能改/何时冻结） | 影响方确认后才能合 |

**看板列**：`待认领 → 进行中 → 待评审 → 待验收（有证据）→ 已完成`。
"待验收"必须附证据，没有证据的不能进"已完成"。

## 8. 决策与文档（避免"谁说了算"的扯皮）

- **ADR（架构决策记录）**：`docs/adr/NNNN-标题.md`，模板四段：背景 / 选项 / 决定 / 后果。
  必须写 ADR 的情形：契约破坏性变更、引入新组件（Redis/Neo4j/队列）、跨仓库边界调整、权限模型变化。
- **设计文档**：任何 **> 3 天**的工作项先写 1 页设计（问题 / 方案 / 接口 / 取舍 / 验收），评审通过再动手。
- **文档即接口**：README 的命令必须能跑（CI 里加一条"README 命令冒烟"最好）；过期文档视同 bug。

## 9. 常见冲突与标准解法

| 冲突场景 | 标准解法 |
| --- | --- |
| 两人都要改同一个契约 | 契约改动**按天排队**，发起人先发预告；小改动合并成一个契约 PR |
| 前端等后端接口 | mock 先行：按契约写 mock，后端实现后切真实地址（一行配置） |
| 数据模型变更影响已有数据 | 必须附 Alembic 迁移 + 回滚脚本 + 在测试库演练过；破坏性变更走 ADR |
| 两人改同一个页面/组件 | 按**功能域目录**切（chat / lineage / metrics / reports），跨域改动先在群里说 |
| 旧内核要改（本次冻结） | 本期一律不改；确有必要则：两边各开 PR + 契约版本号 + 记录 ADR + 通知所有人 |
| "我觉得这样更好" | 写进 ADR 的"选项"里，用验收标准说话，不用偏好吵架 |

## 10. 新人上手路径（第一天就能产出）

1. 读三份文档：本文件 →《项目规划与功能设计 v1.1》§0/§7.4/§8 →《功能点清单与工作分解》§1
2. 跑 `make dev` + `make demo`，把 demo 截图发群里（**第一份产出**）
3. 认领一个"好上手"工作项：`W-104` 分层守卫 / `W-105` 开发环境 / `W-118` 报告代理 / `W-130` 降级态 / `W-128` 报告页
4. 走一遍完整流程：Issue → 契约（如需要）→ 分支 → PR（带证据）→ 评审 → 合并
5. 第二周起，按 Owner 矩阵接一个模块的长期维护
