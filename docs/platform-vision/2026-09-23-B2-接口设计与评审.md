## 1. 现实约束：旧内核真实契约（含 4 个坑）

### 1.1 B2 用到的 5 个端点（真实入参 → 真实出参）

| 内核端点 | 真实入参（实测） | 出参关键字段（实测） | 用途 |
| --- | --- | --- | --- |
| `POST /analyze` | `{mode:'sql', sql:'…', dialect:'hive', depth:3}` | `success, input_tables[3], output_tables[1], table_lineage[3], column_lineage[13]{target_table,target_column,source_table,source_column,expression,resolved}, statements[], knowledge{kb_available,metrics[2],terms[13],rules[4],matched_fields[2]}, report{report_id,url,size_bytes} , report_id, report_url` | 单脚本血缘 + 口径命中（**一个调用同时拿到血缘与口径**） |
| `POST /kb/search` | `{query:'产量'}` ⚠️ 参数名是 `query`（不是 `keyword`） | `success, query, total:72, counts{metrics,fields,tables,terms,rules}, groups.metrics[20]/fields[20]/tables[5]/terms[13]/rules[14]（每条带 score）` | 口径/术语/字段检索（**多命中，需选证据**） |
| `POST /kb/ask` | `{question:'…'}` | `success, intent, intent_label, entity, answer, mode:'rule', llm{enabled:false}, evidence{entity,metrics[]}` | 内核自带的**规则式**问数（意图分类 + 规则答案） |
| `POST /upstream` | `{table:'ads.ads_产销存月报', depth:5}` | `success, direction, start_table, found, direct[3], levels[5], tables[14], upstream_count:14, edge_count:18, paths[9]` | 上游链路（**表级图，来自 warehouse_graph.json**） |
| `POST /impact` | `{table:'cdw.dws_产销存汇总'}` | `success, direction:'downstream', start_table, found, direct[2], levels[3], tables[4], downstream_count:4, edge_count:5, paths[2]` | 下游影响面 |
| `POST /report` | 分析结果 | `{report_id, url, internal_url, path, size_bytes, generated_at}` | 自包含 HTML 报告（实测 20,733 B） |

### 1.2 四个坑（设计必须吃进去）

1. **失败也是 HTTP 200**：`/kb/search` 传错参数得到 `HTTP 200 + {"success":false,"error":"query 不能为空"}`；`/kb/metric` 同理要 `name`。
   → 客户端**必须判 `success` 与 `error`**，不能只看状态码（`lineage-client` 的第一条规则）。
2. **参数名不统一**：`/kb/search` → `query`，`/kb/metric` → `name`，`/upstream` → `table` + `depth`。
   → 平台侧的工具入参必须**归一化**，把差异关在 client 内部（业务层只写 `search_metrics(keyword)`）。
3. **内核自己的规则问数很弱，不能当问答引擎**：实测 `/kb/ask` 问「ads.ads_产销存月报 的产量怎么来的」→ `intent=metric_formula`（对）但 `entity="ads.ads_产销存月报 产量怎么来"`（**整句当实体**）、`evidence.metrics` **0 条**、`answer` 只列出"共 6 条相关口径"的泛化文本。
   → 平台**必须自己做实体识别**（表名 / 字段 / 中文名 / 指标名），`/kb/ask` 的 `intent` 只作**意图信号**复用，答案不直接透传。
4. **内核没有 status / version / 行号**：口径结果里有 `confidence`（如 0.9）、`chinese_source`（`exact_glossary` / `builtin` / `rule` / `pending`）、`source_script`（**只有文件，没有行号**，如 `examples/warehouse/ads/ads_产销存月报.sql`），KB 全局只有 `schema_version:1.0.0` 与 `built_at`。
   → **统一结果模型的 `status`/`version`/`source.line` 必须由平台装配**（§4 给规则，§6 决策点 1/2 定归属）。

### 1.3 「产量怎么来的」的真实数据长什么样（这条最能说明平台的价值）

实测三处命中，**分散在两层、三种实体里**：

| 来源 | 内容 | 说明 |
| --- | --- | --- |
| `/analyze` 字段血缘 | `ads.ads_产销存月报.output_qty ← cdw.dws_产销存汇总.output_qty`，表达式 `s.output_qty AS output_qty`，`resolved=true` | **透传，没有计算**——只看这行会以为"产量就是上游的产量" |
| `/kb/search` 字段词表 | `ads.ads_产销存月报.output_qty` 中文名「产量」，`chinese_source=exact_glossary`，`confidence=1.0` | 只给中文名，**没有公式** |
| `/kb/search` 指标口径 | `cdw.dwd_卷烟产量码段明细`：`产量 = 打码量 + 跳码量 − 重码量`，`confidence=0.9`；另有 `ads.ads_码段产量日报` / `经营指标驾驶舱` 的 `产量 = SUM(产量)` | **公式在 dwd 层**，不在 ads 层 |

**结论（产品主张的落点）**：一句话回答「产量怎么来的」＝ 把 **① ads 层字段的中文名与透传关系 ② 上游链路（3 层） ③ dwd 层的真实公式** 拼成一条可追溯的链——这正是 B2/B3 要做的事，也是**任何单次内核调用都给不出来**的东西。设计里若把它简化为"透传一条分析结果"，产品价值就没了。

## 2. 对话编排管线（一次提问的 7 步）

```
提问(text, session)
 0 归一化   纠正/补全上下文（"它"→上一轮的表），剥掉寒暄
 1 实体识别 表/字段/中文名/指标名 + 时间范围        ← 平台自己做（内核弱，见 §1.2-3）
 2 意图判定 规则层优先（确定性）；置信不足才叫 LLM
 3 工具计划 产出有序工具序列（含参数与依赖）
 4 工具执行 并发执行独立工具；超时/重试；全程记录
 5 证据装配 挑选证据、跨层拼装、算 status/confidence  ← 含金量最高的一步
 6 结果模型 {value,confidence,status,evidence[],source,version} + 回答文本 + 建议追问
 7 审计落库 提问/工具调用/证据/回答 全链路留痕
```

### 2.1 规则层与 LLM 层的分界（判定表）

| 问题形态（规则可判） | 意图 | 工具序列 | 是否要 LLM |
| --- | --- | --- | --- |
| 提到表名 + "怎么来的/来源/上游/血缘" | `table_lineage` | `upstream` →（可选）`report` | 否 |
| 提到表.字段 或 中文名 + "怎么算/口径/公式" | `metric_lookup` | `kb.search` →（若有脚本）`analyze` | 否 |
| 提到表/字段 + "会砸谁/下游/影响" | `impact` | `impact` | 否 |
| 贴了一段 SQL | `script_analyze` | `analyze`（内含口径命中） | 否 |
| 提到"报告/导出/给我看" | `report` | `analyze`/`upstream` → `report` | 否 |
| 复合问句（"产量怎么算的，改了会砸谁"） | 多意图 | 上面的序列**拼接**（`metric_lookup` + `impact`） | 可选（拆句） |
| 以上都不匹配 / 实体缺失 | `unknown` | 不调用工具 → **反问澄清**（"你问的是哪张表？"） | 是（改写澄清话术） |
| 需要把结论写成自然语言、生成建议追问 | — | — | 是（**只做表达，不做事实**） |

**铁律**：LLM 只允许出现在 ① 拆复合句 ② 实体缺失时的澄清 ③ 答案措辞与建议追问。**事实（数字/公式/表名/血缘）一律来自内核**，LLM 不得生成。

### 2.2 规则层的实现要点（无 key 也能跑通验收路径）

- 实体识别：① 精确匹配 `schema.table` 与 `table.column`；② 中文名反查（走 `/kb/search` 的 `fields`/`terms` 组）；③ 会话上下文回填（上一轮表/字段）；④ 兜底把整句当关键词检索（保留内核的稳退行为）。
- 意图判定：先用关键词规则（上表左列）打分；`/kb/ask` 的 `intent` 作为**加分信号**（不单独定案，因为实测它的 `entity` 不可用）。
- 置信不足（no 实体 / 多实体得分接近）→ 进澄清分支（反问），**不允许猜**。

## 3. 工具注册表（B2 交付物之一）

统一工具签名（业务层只见这个，内核参数差异关在 client 里）：

```python
@dataclass
class ToolResult:
    ok: bool
    data: dict          # 内核原始 data（不改写，便于溯源）
    error: str | None
    ms: int
    endpoint: str       # 例 "POST /analyze"，写进审计与工具步骤条

class LineageTool(Protocol):
    def analyze(sql: str, dialect: str = "hive", depth: int = 3) -> ToolResult: ...
    def upstream(table: str, depth: int = 5, graph: str | None = None) -> ToolResult: ...
    def impact(table: str, direction: str = "downstream") -> ToolResult: ...
    def search(keyword: str, kinds: list[str] | None = None, limit: int = 20) -> ToolResult: ...
    def ask(question: str) -> ToolResult: ...          # 仅取 intent 信号
    def make_report(payload: dict) -> ToolResult: ...   # 返回 {report_id,url,size_bytes}
```

| 工具 | 映射 | 超时 | 重试 | 幂等 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `analyze` | `POST /analyze` | 30s | 1 次（连接类错误） | 是 | 会**落盘报告**（副作用：多一份 HTML），同 SQL 建议按 hash 缓存 |
| `upstream` / `impact` | `POST /upstream` / `/impact` | 10s | 1 次 | 是 | 读 `warehouse_graph.json`，无副作用 |
| `search` | `POST /kb/search`（`query`） | 10s | 1 次 | 是 | 一次检索 5 组命中，**必须做证据挑选**（§4.3） |
| `ask` | `POST /kb/ask` | 10s | 0 | 是 | 只读 `intent`/`intent_label` |
| `make_report` | `POST /report` | 30s | 0 | 否（每次新 id） | P1 的"导出报告"入口；报告 URL 直接给前端 |

**错误规范**：`success=false` → `ToolResult(ok=False, error=内核 error 文本)`，**原样透传给审计**（便于定位是平台还是内核的问题）；`evidence` 里只放 `ok=True` 的结果。

## 4. 统一结果模型的装配规则（谁填、什么时候能填）

### 4.1 字段来源表

| 字段 | 来源 | 装配规则 |
| --- | --- | --- |
| `value` | 内核 | 公式类取 `formula`（人话）+ `formula_full`（忠实）；数值类取字段/指标表达式；**没有就不给数字** |
| `confidence` | 内核 `confidence` | 多证据时取**证据链最小值**（不取平均，避免被高分掩盖） |
| `status` | **平台推导**（§4.2） | 内核无此字段 |
| `evidence[]` | 内核多端点 | 每条含 `type/ref/summary/source{file,line?}/endpoint` |
| `source` | 内核 | 优先 `source_script`（文件）；行号见 §6 决策点 2 |
| `version` | **平台推导** | P1 用 `kb:{schema_version}@{built_at 日期}`（如 `kb:1.0.0@2026-09-20`）+ 报告 id；**P2 引入平台口径审核表后换成人审版本号** |

### 4.2 `status` 判定表（**请重点评审**）

| 内核迹象（实测可得） | 判定 | 理由 |
| --- | --- | --- |
| `chinese_source = exact_glossary` 且 `confidence = 1.0` | `verified` | 来自**人工维护**的词表（P1 能拿到的"最像已审核"的证据） |
| 指标口径命中且 `confidence ≥ 0.9`，有 `source_script` | `verified` | 口径由脚本推导 + 脚本位置明确 |
| 有字段血缘但字段/指标只匹配到中文名（无公式） | `inferred` | 链路成立、口径未定 |
| 命中靠模糊匹配（`score` 低、表名不一致） | `candidate` | 仅供参考，界面必须写"候选口径，请确认" |
| `chinese_source = pending`（KB `pending_terms=1`） | `candidate` | 待审核术语 |
| 字段血缘 `resolved = false`，或工具 `success=false` | `unresolved` | 证据不足 |
| 内核 KB 快照（`schema_version`+`built_at`）与平台记录不一致 | `stale` | 需重新同步 |

> **诚实说明**：P1 的 `verified` 含义是"来自人工维护的词表/脚本推导"，**不等于"平台人工审核通过"**——真正的审核态需要平台侧的口径审核表（P2，规划里已有）。若你要 P1 就严格区分，我们把它拆成 `verified(glossary)` 与 `reviewed` 两档（见决策点 1 的选项 C）。

### 4.3 证据挑选算法（`search` 一次返回 72 条命中的问题）

输入：实体（`schema.table` / `table.column` / 中文名）+ 问题意图。打分（从高到低）：
1. **表完全匹配**（`table_name == 实体表`）→ +100；字段名匹配 → +60；中文名匹配 → +40
2. **层次加权**：`ads`（业务直达）+15 / `dws` +10 / `dwd` +8 / `ods` +5
3. **来源加权**：`exact_glossary` +30 / `rule` +15 / `builtin` +5 / `pending` 0
4. **公式可得性**：有 `formula` +25（"怎么算"类问题必需）
5. 同分时按 `score` 高者；**最多取 3 条**作为证据（血统链上每层最多 1 条）
- 跨层拼装：`ads 字段(中文名) → 上游层次 → dwd 公式` 串成链（§1.3 的真实场景），链上每一跳都带 `source`。

### 4.4 边界行为（铁律落地）

- `evidence == []` → **不允许出结论数字/公式**，改为："我只查到 X，还差 Y，建议…" + 反问；`status=unresolved`。
- 多证据互相矛盾（同字段两条口径，公式不同）→ 都列出，`status=candidate`，标出差异点，并给"提交口径仲裁"入口（P2 接审核台）。
- LLM 不可用 → `mode='rule'`，答案文本由模板生成（**数据仍真实**），顶栏亮"规则模式"。

## 5. 三个关键用例（伪代码 + 期望输出）

### 用例 1：`ads.ads_产销存月报 的产量怎么来的？`（验收主路径）

```python
def handle(q):
    ent = extract(q)                      # {table:'ads.ads_产销存月报', field_word:'产量'}
    intent = classify(q, ent)             # 'metric_lookup' + 'table_lineage'
    plan = [upstream(ent.table, depth=3),               # ① 表级链路
            search(f"{ent.table} {ent.field_word}"),    # ② 该表字段词表（拿中文名/置信度）
            search(ent.field_word, kinds=['metrics'])]  # ③ 全局公式口径（含 dwd 层）
    rs = run(plan)                        # 并发；每个 ToolResult 记 ms
    ev = assemble(rs, ent)                # §4.3：链路 + 词表 + 公式（最多 3 条）
    return build_answer(ev)               # 结论 + status + evidence + 建议追问
```
**期望输出（基于真实数据）**：
```
产量 = 打码量 + 跳码量 − 重码量            ← 公式来自 cdw.dwd_卷烟产量码段明细（conf 0.9）
本表 ads.ads_产销存月报.output_qty 是上游透传（表达式 s.output_qty AS output_qty，resolved）
链路：ods.ods_卷烟产量明细 → cdw.dwd_卷烟产量明细 → cdw.dws_产销存汇总 → ads.ads_产销存月报（14 张上游 / 18 条边）
status = inferred（口径来自脚本推导，非人工审核）  confidence = 0.9  version = kb:1.0.0@2026-09-20
凭证：血缘图（/upstream）· 口径卡（/kb/search）· HTML 报告 rpt_20260923_211028_a794d3f0（20,733 B）
```
⚠️ 注意：**公式不在 ads 层**——若实现时只取"本表命中"，会答成"透传上游"，这是错的。这条用例就是用来抓这个错的。

### 用例 2：`改 cdw.dws_产销存汇总.output_qty 会砸哪些下游？`

```python
plan = [impact('cdw.dws_产销存汇总', direction='downstream')]
```
**期望输出**：`下游 4 张表 / 5 条边`（实测）＋ level 分层列表 ＋ 导出入口。`status=verified`（图数据确定），无口径依赖。

### 用例 3：无 LLM key 的降级

- `mode='rule'`；用例 1、2 的**数据完全一致**，只是话术由模板生成；顶栏亮"规则模式"并注明原因（未配置 key）。
- 验收：跑 `pytest tests/test_agent_rule_mode.py`——同一批用例在 `LLM_ENABLED=false` 下断言 **结论/证据/status 与开启时一致**（只允许措辞不同）。

## 6. 待拍板（三个决策点）

### 决策点 1：`status` / `version` 归谁

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 平台推导（§4.2 判定表）+ P2 建平台口径审核表把 `verified` 升级为"人审" | 内核零改动；`verified` 语义暂时弱（需在界面文案说明） |
| B | 现在改内核契约，让内核返回 `status/version` | 违反 Phase 0「冻结内核」，且要动旧仓库测试 |
| C | P1 就拆两档 `verified(glossary)` / `reviewed(平台人审)`，`reviewed` 先恒为空 | 语义最准，前端要多处理一档（成本小） |

### 决策点 2：`source.line`（行号）从哪来

现状：内核只给 `source_script = examples/warehouse/ads/ads_产销存月报.sql`，**无行号**；而《设计说明书》§3.3 承诺"来源到文件+行号"。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 内核**新增只读端点** `POST /kb/source {file, needle}` → 返回片段与行号 | 内核加 1 个端点（**只新增，不改现有契约**，向后兼容） |
| B | 在 `/kb/search` 的结果里**加字段** `source_line` | 改动既有响应结构（兼容但动了现有代码/测试） |
| C | 平台只展示**文件级**来源，界面标"行号 P2 补" | 内核零改动；需**改设计说明书文案**，溯源强度下降 |

### 决策点 3：LLM 与规则的分界

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 规则优先，LLM 兜底（只在 拆句/澄清/措辞 三处） | 无 key 也能跑通验收；复杂问句体验一般 |
