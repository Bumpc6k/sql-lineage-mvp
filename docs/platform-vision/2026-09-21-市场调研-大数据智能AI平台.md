# 市场调研：大数据智能 AI+ 平台（对话优先 · 纳管调度 · 血缘口径 · 生成落地）

日期：2026-09-21　调研方式：22+16 组关键词检索 + 8 个关键页面精读（含厂商官方页、GitHub 仓库、行业报告）
结论口径：**只写能指到来源的事实**；厂商自报数据标注为"厂商口径"

---

## 0. 一句话结论

你要做的东西，市场上有三个"半成品"分别做掉了它的三段，**没有一家把它连成一条链路**：

- **做技术血缘的**（DataHub / OpenMetadata / Atlas / DataWorks 地图）→ 有表级/字段级血缘，**没有业务口径，也不管调度运维**
- **做对话问数的**（DataWorks Copilot、Quick BI 小Q、析言GBI、SuperSonic）→ 能自然语言取数/生成代码，**不管血缘追溯，也不生成可落地的任务流**
- **做调度与原厂运营的**（DolphinScheduler、WhaleStudio）→ 有编排/运维，**往上做的"Agent 控制平面"是 2026 年的新方向，但绑定自家调度**

**所以定位建议是**：不推倒重来，而是把已建成的"血缘内核 + 口径库 + 生成引擎 + 海豚旁路"升格为**平台底座**，在上面新增一个**对话优先的门户层**，并补一个**多调度接入层**。差异化一句话：

> **把调度平台上已经跑着的数据链路，变成可对话、可追溯、可生成的业务知识资产。**

## 1. 市场分层：我们站在哪一格

行业报告《2026 爱分析·Data+AI 厂商全景报告》把市场划成**四层架构 + 七大细分市场**（本体平台、语义平台、DataOps、智能体开发平台、通用 Data Agent、工业 Data Agent、决策智能平台）——来源：<https://www.ifenxi.com/research/content/6834>

| 层 | 干什么 | 代表 | 我们的对应 |
| --- | --- | --- | --- |
| 数据底座 | 加工、治理、存储 | 湖仓 / DWS / Hive | 复用客户已有（不重做） |
| **语义层** | 业务上下文、指标口径、血缘 | 语义平台厂商、dbt Metrics、Cube | **已有** `knowledge/` 口径库 + 血缘图谱 → 要升级成"语义层" |
| **DataOps** | 编排、调度、运维 | DolphinScheduler、Airflow、DataWorks | **要新增**多调度接入层 |
| **Data Agent** | 对话式问数、生成、执行 | DataWorks Copilot、Quick BI 小Q、网易知数、WhaleStudio DataAgent | **要新增**对话门户（核心交互） |

结论：我们的新平台 = **语义层 + DataOps + Data Agent 三层的纵向打通**，而不是再做一个第 N 个单点工具。

**一眼可读的三个结论**：
1. 右三列（对话 / 生成 / 运维）里，**"多调度纳管"整行为空** —— 这是最干净的空白格。
2. **业务口径固化几乎整列为空** —— 与我们既有判断一致（技能库《血缘与指标口径知识层》里已记录）。
3. DataWorks 与 WhaleStudio 是唯二把"对话 + 生成 + 落地"连起来的产品，但**一个绑阿里云、一个绑自家调度**。

## 3. 六个"最接近但不等价"的玩家

### 3.1 WhaleStudio（WhaleOps，DolphinScheduler 商业版）——**最直接的对标**
官方首页把自己定位成 **"Data Engineering Agentic Control Plane"**：让 Codex / Claude Code 这类 AI agent 能**安全地 build / run / govern 企业数据工作流**，口号是 *"AI-callable, human-reviewable, enterprise-governed"*，能力块包含 **RBAC & Access Control**、Agent Execution Trace。来源：<https://www.whaleops.io/>
→ **启发性**：① "Agent 控制平面"这个词说明原厂也在往"对话/Agent 优先"走；② 它证明"生成后必须人工可审、可回滚"是刚需；③ **它是商业授权**（有 EULA 文件），而且绑自家调度 → 我们的空间是"开源可私有化 + 不绑调度"。

### 3.2 DataWorks（阿里云，Data + AI 一体化）——**能力最全的 SaaS 对手**
Data Studio 支持 Python/Notebook、CPU/GPU 混合资源池、PAI Flow 可视化编排，**"自动生成全域数据血缘图谱"**；**DataWorks Copilot** 做 SQL/Python 的**生成、续写、改写、优化、解释、纠错与测试用例生成**，厂商口径称平均提效 35%。来源：<https://juejin.cn/post/7483049212314943523>、<https://help.aliyun.com/zh/dataworks/user-guide/overview/>
→ **边界**：绑阿里云、不开源、不能私有化，且**不纳管别家调度**。

### 3.3 SuperSonic（腾讯音乐，开源 Chat BI + Headless BI）——**开源里最像"对话问数"的**
"融合 Chat BI（LLM 驱动）与 Headless BI（语义层驱动）"，在物理模型上建**逻辑语义模型（指标/维度/实体/标签）**，用语义检索增强 Text2SQL *以减少幻觉*，对话出结果并自动选图。来源：<https://github.com/tencentmusic/supersonic>
→ **边界**：它解决的是"**取数**"（查询/看板），**不做血缘解析、不生成任务流、不管调度**；许可为 Apache 2.0（社区镜像页提到带附加条款，商用前需核对原文）。
→ **启示**：它的"语义层增强 Text2SQL"正好是我们**口径库**能做的事 —— 口径库未来应该演进成"语义层"，用口径约束生成的 SQL，而不是只给人看。

### 3.4 网易数帆 全链路数据智能平台 V10.0 ——**厂商在用同一套叙事**
四项能力联动：数据开发治理 + **指标语义管理** + 有数 BI + **知数 DataAgent**，实现"从接入、治理、分析到智能决策的全链路闭环"。他们的原话很值得引用：*"AI 再聪明，如果底下的口径不统一、血缘不清楚、治理不闭环，问得越快，决策越乱。"* 来源：<https://www.geekpark.net/news/369937>
→ **启示**：我们过去两年做的事情（口径 + 血缘 + 治理），正是"AI 问数"能不能落地的前置条件 —— 这套叙事可以直接用在方案与面试里。

### 3.5 DB-GPT（开源，AI Native 数据应用框架）——**"对话 + 数据"的开源底座**
定位 "AI Native Data App Development framework"，自带 AWEL 工作流编排、多数据源、对话界面。来源：<http://docs.dbgpt.cn/docs/overview>
→ **边界**：它是**框架/工具箱**，不预置"血缘解析 + 口径固化 + 调度纳管"的领域能力，需要自己灌业务。

### 3.6 DataSphereStudio + Apache Linkis（微众 WeDataSphere）——**"一站式开发门户"的早期形态**
DSS 是"one stop data application development management portal"，**支持把工作流发布到 Airflow 调度**（说明"门户纳管多调度"的原型早已存在），底层依赖 Linkis 计算中间件做统一作业提交。来源：<https://github.com/WeBankFinTech/DataSphereStudio>、<https://github.com/apache/linkis>
→ **边界**：以"脚本开发 + 工作流发布"为中心，**没有 AI 对话、没有口径知识层**；活跃度需自行核实（本次未取到可靠证据，故不做结论）。

### 3.7 元数据平台集体转向"AI 上下文层"（趋势信号）
OpenMetadata 2026-04 的 1.13 自称 *"open source semantic context layer for AI-ready data teams"*，2026-08 的 2.0 直接叫 *"The Open Context Layer for AI Agents"*。来源：<https://blog.open-metadata.org/announcing-openmetadata-1-13-123d66609468>、<https://blog.open-metadata.org/announcing-openmetadata-2-0-the-open-context-layer-for-ai-agents>
→ **启示**：连元数据平台都在抢"给 AI 供上下文"的位置。我们的血缘 + 口径天然就是"上下文"，**把它做成 MCP/API 提供给任意 Agent**，是一条低成本高价值的路线。

## 4. 空白点（可论证的差异化）

| # | 空白 | 论证 |
| --- | --- | --- |
| 1 | **业务口径固化（提炼→人审→版本→注入生成）** | 对标矩阵几乎整列为空；已有开源/商业产品只做技术血缘。我们的 `knowledge/` 已经跑通"两阶段提炼 + 置信度 + 幂等指纹" |
| 2 | **多调度平台统一纳管（含运维动作）** | 元数据工具只"采集"、门户只"发布到某个调度"，**没有开源产品做"海豚 + DataWorks + Airflow 同一控制台的监控/重跑/补数"** |
| 3 | **对话作为主入口的开源可私有化实现** | 对话主入口只有大厂 SaaS（Copilot / 小Q / 知数）与商业版（WhaleStudio）；开源侧只有 Chat UI 与框架，**没有把"对话 → 血缘/口径 → 生成 → 落地调度"串起来的成品** |
| 4 | **生成物的安全落地**（草稿 → 人工审核 → 落调度 → 可回滚 + 审计） | WhaleStudio 在讲这个故事（"human-reviewable, governed, reversible"），但绑自家调度；我们已有海豚侧"只读旁路 + 幂等补丁"的工程经验可平移 |

| `apps/lineage-api/render`（HTML 报告） | 报告中心（可下载/可分享的凭证） | 保留 |

| `contracts/openapi.yaml` + 分层守卫 | 平台级契约与边界治理 | 扩成多单元契约 |

## 7. 定位建议（一句话）

> **面向已建有调度平台的企业，做一个"对话优先的数据智能平台"：纳管调度（海豚/DataWorks/Airflow）、解析存量链路（表级/字段级血缘）、提炼业务口径（人审+版本）、并用口径约束反向生成 SQL 与任务流，生成物必须可审、可回滚、可审计。**

**三条差异化护城河**：① 业务口径固化（市场空白）；② 多调度纳管（市场空白）；③ 对话即入口的可私有化实现（大厂有、开源无）。

**三条必须先想清的风险**（写方案时必须带）：
1. **纳管写操作 = 生产风险**：重跑/补数必须有审批 + 审计 + 二次确认，先只读、后写；
2. **口径责任边界**：LLM 只产候选，人工审核不可省（错了污染全公司指标）；
3. **范围失控**：平台化最容易变成"什么都做，什么都没做完"，必须有 P1 的"窄而通"闭环。

## 8. 建议路线（详细规划留到下一份文档）

| 阶段 | 目标 | 验收（能拿出来演示的东西） |
| --- | --- | --- |
| **P1 门户骨架 + 对话闭环** | 登录/权限/菜单 + 会话式首页 + 血缘/报告/口径三域（对话里就能调） | 打开浏览器 → 登录 → 在对话里问"这个字段从哪来" → 出答案 + 可点报告 |
| **P2 生成闭环 + 运维只读** | 需求→SQL/任务流→**人工审核**→落海豚；任务实例监控/日志/只读运维 | 一句话生成工作流并落到海豚跑通；能看实例、能看日志 |
| **P3 多调度纳管 + 语义层** | DataWorks/Airflow 适配器；口径库升格为语义层，约束生成 | 同一控制台看到两种调度的任务；生成的 SQL 能被口径校验 |
| **P4 开放与生态** | Agent/MCP 开放（把血缘+口径喂给任意 Agent）、飞书/CLI 同源、插件市场雏形 | 外部 Agent 能通过 MCP 取到我们的血缘与口径 |

## 9. 需要你拍板的 5 个问题（下一份规划文档的前置）

1. **形态**：新平台是"在 `sql-lineage-mvp` 里长出来"，还是**新开一个仓库**（如 `data-intelligence-platform`），把现有模块作为依赖引进去？
2. **后端栈**：门户后端用 **FastAPI**（推荐，生态/文档/自动 OpenAPI），还是继续标准库 `http.server`（零依赖但平台期会很难受）？
3. **认证**：自研登录（简单但要做用户/角色/菜单三张表）还是**独立部署 Casdoor**（OIDC，省掉登录页与用户体系）？
4. **纳管范围**：P1~P2 是否**只做海豚**（窄而深，先跑通闭环），还是同时开 DataWorks 适配器（广而浅）？
5. **前端栈**：Vue 3 + Vite + TS + **Ant Design X**（对话组件）+ vben-admin 骨架，是否就这样定？
