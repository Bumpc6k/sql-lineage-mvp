| --- | --- |
| **定位（一句话）** | 面向已建有调度平台的企业，做**对话优先的数据智能平台**：纳管调度、解析存量链路、固化业务口径、按需反向生成 SQL 与任务流 |

## 1. 定位与边界

### 1.1 是什么

一个**位于调度平台之上、面向"人 + Agent"的数据智能层**：
- 往下：通过适配器**纳管**已有调度平台（DolphinScheduler / DataWorks / Airflow），只读为主，运维动作审批后可写
- 中间：把平台上**已经跑着的**脚本与任务流解析成**技术血缘（表级/字段级）**与**业务口径知识**（人审 + 版本）
- 往上：以**对话**为统一入口，做问数、影响分析、需求→SQL/任务流生成、并把生成物**安全落地**回调度平台

### 1.2 不是什么（写清楚，防止范围失控）

| 不做 | 原因 / 替代 |
| --- | --- |
| 不重做存储与计算引擎 | 用客户已有的 Hive/Doris/DWS/湖仓 |
| 不做通用 BI 图表工具 | 可对接既有 BI（帆软/Quick BI）；平台只给"可点开的凭证"（报告/图谱） |
| 不重复建设元数据采集能力 | 需要时**对接** DataHub / OpenMetadata（把我们的血缘与口径推给它们，借它们的生态） |
| 不做数据质量规则的重复建设 | DolphinScheduler 3.0+ 原生数据质量、DataWorks 已覆盖 → 我们只做"链路质量体检"（断链/孤岛/未登记口径） |
| P1 不做写操作 | 纳管写操作 = 生产风险，先只读建立信任 |

### 1.3 与竞品的关系（调研结论的落地）

- **WhaleStudio（海豚原厂）**走"Agentic 控制平面 + 绑自家调度"，是商业授权 → 我们做**开源可私有化 + 不绑调度**
- **DataWorks Copilot / Quick BI 小Q / 析言GBI / 网易知数**证明"对话入口"是共识，但都绑自家云 → 我们做**可私有化、跨平台**
- **SuperSonic（腾讯开源）**证明"语义层约束 Text2SQL"是对的 → **我们把口径库升格成语义层**（这是我们的既有资产）
- **DB-GPT / DSS**是框架与门户，缺领域能力 → 我们填的是**领域闭环**（血缘+口径+生成+落地）

### 1.4 复用清单（评审必答：哪些是别人的能力）

| 能力 | 来源 | 我们只做增量 |
| --- | --- | --- |
| 调度编排/重试/补数机制 | DolphinScheduler / DataWorks 原生 | 统一入口 + 审批 + 审计 + 跨平台视图 |
| 任务级/表级血缘 | 海豚 3.3.1+ `t_ds_workflow_task_lineage`、DataHub/OM | **字段级血缘** + **跨平台合并** + **业务口径** |
| 登录/SSO | Casdoor（OIDC） | 平台侧 RBAC（菜单/按钮/数据权限）与审计 |
| 对话 UI 组件 | Ant Design X（或 Vue 社区移植） | 数据域专用卡片：血缘图/字段表/口径卡/报告卡 |
| SQL 解析 | sqlglot（已用） | 方言适配、变量渲染、置信度标注 |

### 2.2 两个仓库的耦合方式（三选一 + 推荐）

| 方式 | 说明 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A. HTTP 契约**（P1 采用） | 门户通过 `contracts/openapi.yaml` 调 18080 | 零改动、可独立部署与替换、边界最硬 | 每次调用有网络+序列化开销；Agent 高频调用时可能慢 | ✅ **P1 就用它** |
| **B. 进程内包依赖**（P3 演进） | 把 `knowledge/`、`generate/` 也抽成 pip 包，门户进程内 `import` | 快、调试方便、事务一致 | 两仓库的发布节奏耦合；旧仓库要配合重构 | ✅ **P3 按需切换**（先抽 `lineage-knowledge`、`lineage-generate`） |
| C. git submodule / subtree | 直接把旧仓库嵌进来 | 单仓库视角 | 版本地狱、双写风险 | ❌ 不用 |

**策略**：契约先行。门户**只认契约**（openapi），不 import 旧仓库任何内部模块 —— 这样 P3 换成进程内依赖时，门户代码零改动（换适配器实现即可）。

## 3. 技术栈选型

> 原则：**越贴近"能私有化、能自己维护、能在 Windows/WSL 上跑起来演示"越好**；每个选型标注代价与替代方案。

### 3.1 后端

| 层 | 选型 | 为什么 | 代价 / 替代 |
| --- | --- | --- | --- |
| Web 框架 | **FastAPI**（Pydantic v2） | 类型即文档、自动 OpenAPI（正好服务"契约先行"）、异步适合 Agent 编排 | 生态比 Django 薄 → 管理后台类功能要自己写；替代：Django（自带 admin，但契约与异步弱） |
| ORM / 迁移 | **SQLAlchemy 2 + Alembic** | 成熟、迁移可控 | 比 SQLModel 啰嗦，但可控性更好 |
| 平台元数据库 | **PostgreSQL 16** | 用户/角色/会话/审批/审计/快照都适合；JSONB 存消息与快照很省事 | 运维成本 → docker-compose 一键起 |
| **血缘图存储** | **Neo4j（P1 就上）** | 多跳血缘/影响分析是核心能力，**关系库递归 CTE 在多跳时会崩**（技能库既有结论）；Neo4j Browser 顺带解决"图谱可视化" | 多一个容器；替代：NebulaGraph（更大规模），或 P1 用 PG 邻接表限制 ≤3 跳（**不推荐，早晚要迁**） |
| 缓存 / 队列 | **Redis 7** + **arq**（轻量）→ 后期 Celery | 会话缓存、限流、异步任务（解析、报告生成、补数） | arq 生态小；若已有 Celery 经验直接用 Celery |
| 全文检索 | **PG 全文 + trigram**（P1）→ 需要再上 ES | 少一个组件；口径/术语/表名的中文检索可用 Python 侧分词兜底 | 中文分词是坑（zhparser 需装扩展）→ P1 用 jieba 预切 + trigram，标注为临时方案 |
| 向量检索 | P3 按需引入（pgvector 优先） | 语义问数需要时再加，不提前背 | 后引入需要重建索引 |
| LLM 接入 | **可插拔网关**：OpenAI 兼容 / 本地 vLLM / **无 key 时规则降级** | 演示不需要外部凭据（旧仓库已验证这条路）；企业可换本地模型 | 规则降级的能力边界要写清（复杂语义会退化） |

### 3.2 前端（含一个必须你拍板的取舍）

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | **Vue 3 + Vite + TS** | 与旧仓库既有前端一致；纯前端项目，不需要 React/Next 的全栈生态 |
| 基础组件 | **Ant Design Vue** | 中后台成熟、表格/表单/树够用 |
| 后台骨架 | **vue-vben-admin**（取其布局/权限/菜单模式） | 省掉"登录后框架"的重复劳动；**权限校验逻辑仍写在 portal-api**（前端只做展示级控制） |
| 血缘图可视化 | **AntV G6**（图）+ ECharts（统计） | G6 有现成的层次/力导向布局；也可用 dagre 自算布局 + SVG |
| 状态/路由 | Pinia + Vue Router | 标准组合 |
| **对话 UI 组件** | 见下方"取舍" | ⚠️ 这是唯一需要你拍板的技术点 |

**对话组件的取舍（必须知情）**：
- **Ant Design X 官方只有 React 版本**（官方 FAQ 原话："目前 Ant Design X 只提供 React 版本"）。Vue 侧有社区移植 **`ant-design-x-vue`**（TypeScript，`npm i ant-design-vue ant-design-x-vue`，提供 Bubble / XProvider 等组件），但它是**单一维护者的社区项目**，跟官方版本可能滞后。
- 三条路：
  - **路 A（推荐）**：Vue + `ant-design-x-vue`，对话 UI 直接复用；若该库维护停摆，退回自研（对话 UI 本质是"消息列表 + 输入框 + 流式渲染"，自研约 1~2 人周，不影响平台其他部分）
  - **路 B**：前端改用 **React + Ant Design Pro + 官方 Ant Design X** → 对话组件官方长期支持，生态最全；代价是与你现有前端资产分叉、招人心智切换
  - **路 C**：Vue + 只借鉴 Ant Design X 的**设计规范**，对话 UI 全自研（可控性最高，工作量最大）
- 我的建议：**路 A**。理由：对话 UI 不是本项目的技术难点（难点在 Agent 编排与数据能力），不值得为它换整个前端栈；同时把"对话 UI 与业务 UI 解耦"（独立目录 `portal-web/src/chat/`），万一要换成路 B/路 C，只换一层。

### 3.3 认证与权限

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 身份认证 | **Casdoor（开源 IAM，OIDC）独立部署** | 省掉自研登录页/用户表/密码策略/短信邮件；开源（Apache 2.0），有官方 Docker 镜像（源码构建需 Go 1.21+ / Node LTS / Yarn 1.x）；支持 OIDC 标准客户端接入 |
| 平台侧权限 | **RBAC 自研**（用户 / 角色 / 菜单 / 按钮 / 数据域） | 权限点与业务强相关（如"能否审批补数单""能看哪些项目空间"），必须平台侧实现；可参考 Casbin 的策略模型 |
| 数据权限 | 项目空间（租户）隔离 + 血缘/口径按项目空间过滤 | 烟草场景：按业务域/单位隔离 |
| 审计 | 所有写操作与敏感读操作落审计表（谁/何时/做了什么/结果/IP） | 纳管类平台上线必查项 |

### 3.4 工程与部署

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 本地/单机部署 | **docker-compose**（postgres/redis/neo4j/casdoor/portal-api/scheduler-adapter） | 一条命令起全部依赖；演示环境就在 WSL 里跑 |
| 容器化 | 每个 app 一个 Dockerfile（多阶段构建） | 前端构建产物由 portal-api 或独立 nginx 托管（**P1 用 nginx，体现前端独立部署**） |
| CI | GitHub Actions：lint + 单测 + 契约漂移检查 + 前端构建 | 与旧仓库同款门禁思路 |
| 可观测 | 结构化日志（JSON）+ 审计表 + 简单指标页（/metrics） | P1 不引 Prometheus，先把日志与审计做扎实 |
| 密钥管理 | `.env` + docker secrets（P2 起） | 凭据绝不进节点参数/前端（沿用旧仓库纪律） |

## 4. 架构与模块

### 4.1 分层（自上而下，禁止反向依赖）

```
① 交互层   portal-web（对话工作台 / 血缘中心 / 口径中心 / 生成中心 / 运维中心）
             └─ 飞书机器人、CLI  ← 与 Web 共用同一套 Agent 后端（同源会话）
② 应用层   portal-api：认证鉴权 · 会话管理 · Agent 编排 · 审批流 · 审计 · 告警 · 通知
             packages/dip-agent（意图分类 → 工具编排 → 结果组装 → 引用溯源）
③ 智能层   dip-agent 内置：语义层客户端（口径约束） · LLM 网关（可插拔/可降级） · 工具注册表
④ 集成层   scheduler-adapter：统一任务模型 + 适配器（DolphinScheduler / DataWorks / Airflow）
             lineage-api 客户端（HTTP 契约）：解析 / 口径 / 报告 / 生成
⑤ 内核层   复用旧仓库：lineage-core（sqlglot 解析） · knowledge（口径） · generate（生成） · render（报告）
             血缘图落库：Neo4j（平台侧持久化 + 多跳查询）
```

### 4.2 部署单元与职责（P1 四个，P3 可再拆）

| 单元 | 端口 | 职责 | 不负责 |
| --- | --- | --- | --- |
| `portal-web` | 5173（dev）/ 80（prod） | 全部页面与交互；只通过 HTTP 调 portal-api | 不做权限判定（只做展示级隐藏） |
| `portal-api` | 18100 | 认证、会话、Agent 编排、审批、审计、告警、与内核/适配器通信 | 不直连目标数仓；不解析 SQL（交给内核） |
| `scheduler-adapter` | 18110 | 统一任务模型；拉取工作流/实例/日志；执行"被批准的运维动作" | 不做权限判定（由 portal-api 传入已批准的工单号） |
| `lineage-api`（旧仓库） | 18080 | 解析、血缘、口径、报告、生成 | 不认识用户与会话（无状态服务） |

### 4.3 模块职责（packages）

| 包 | 职责 | 关键约束 |
| --- | --- | --- |
| `dip-core` | 领域实体（用户/会话/消息/口径/血缘节点/工单/审计）、仓储接口、领域事件 | **不 import 任何 Web/DB 框架**（可纯函数单测） |
| `dip-contracts` | Pydantic 契约；生成 openapi.yaml 与前端 TS 类型 | 只允许**追加**字段；破坏性变更升 `/v2` |
| `dip-agent` | 意图分类、工具注册表、会话上下文、LLM 网关、结果组装与引用溯源 | 工具实现通过接口注入（便于替换与降级） |

### 4.4 依赖规则（用 `tools/check_layering.py` 强制）

- 只允许 ①→②→③→④→⑤ 单向；
- `dip-core` 不许依赖任何上层；
- 交互层不许 import 集成层/内核层内部实现（只能走契约）；
- 每个外部平台（海豚/DataWorks/Airflow）只允许在 `scheduler-adapter/adapters/<name>/` 内实现，**公共层不许出现平台特有名词**。

## 7. 数据模型（概念级）

### 7.1 实体与归属

| 实体 | 关键字段（概念） | 存储 | 备注 |
| --- | --- | --- | --- |
| 用户 / 角色 / 权限点 | 用户↔角色↔权限点（菜单/按钮/数据域） | PG | 身份来自 Casdoor，权限在平台侧 |
| 项目空间 | 名称、业务域、成员、可见范围 | PG | 数据隔离的最小单位 |
| 调度连接 | 平台类型、地址、凭据（加密）、同步状态 | PG | 凭据只存密文，日志与前端绝不出现 |
| 工作流快照 / 任务快照 | 平台、项目、工作流标识、任务定义 JSON、抓取时间、内容指纹 | PG（JSONB） | 快照式存储，便于"某个时刻的血缘是什么" |
| 表 / 字段元数据 | 库表名、层、中文名、负责人、首次发现/最近出现 | PG | 中文名与词典相关 |
| 血缘边 | 源（表/字段）、目标（表/字段）、表达式、来源脚本+行号、置信度、解析器版本 | **Neo4j** | 多跳查询；PG 只存统计与索引副本 |
| 口径 | 名称、类型、人话公式、忠实表达式、依赖字段、来源证据、状态、置信度 | PG | 与字段是多对多 |
| 口径版本 / 审核单 | 版本号、diff、审核人、意见、时间 | PG | 变更留痕与回滚 |
| 会话 / 消息 | 会话标题、参与者、消息角色、内容（结构化）、引用（表/字段/口径/报告）、工具调用记录与耗时 | PG（JSONB） | 支持分享与审计 |
| 报告 | ID、类型（单脚本/工作流）、来源、文件路径、大小、生成人、保留策略 | PG + 文件系统 | 报告本体是文件 |
| 生成任务 / 生成物 | 需求原文、产物（SQL/链路 JSON）、自检结果、审核状态、落地结果 | PG | 可回溯、可回滚 |
| 运维工单 / 审计 | 动作类型、目标、申请人、审批人、执行结果、影响面快照 | PG | 纳管写操作的唯一入口 |
| 告警规则 / 事件 | 规则表达式、渠道、触发记录、静默窗口 | PG | 通知走飞书/邮件 |

### 7.2 关系速览

```
项目空间 ─┬─ 调度连接 ─→ 工作流快照 ─→ 任务快照 ─┬─→ 血缘边（写表/读表）
          │                                        └─→ 实例快照 ─→ 告警事件 / 运维工单
          ├─ 表元数据 ── 字段元数据 ──┬─→ 口径（依赖/产出）
          │                            └─→ 血缘边（字段级）
          ├─ 报告（单脚本/工作流）
          └─ 生成任务 ─→ 生成物 ─→ 审核单 ─→ 落地（工作流快照）

会话 ─→ 消息 ─→ 引用（表/字段/口径/报告）  ／  消息 ─→ 工具调用记录 ─→ 审计
用户 ─→ 角色 ─→ 权限点（菜单/按钮/数据域）
```

### 7.3 关键设计点（避免后期返工）

1. **快照而非覆盖**：工作流/任务/实例都存快照 + 内容指纹 → 能回答"上周三那条血缘是什么样"，也让"增量解析"可验证（指纹不变即未变）。
2. **置信度与来源必存**：血缘边与口径都带 `source`（脚本+行号）、`parser_version`、`confidence`，否则无法做"解析质量体检"。
3. **凭据只存密文**：调度连接与模型 Key 走加密列，日志/前端/插件节点参数一律不出现（沿用旧仓库纪律）。
4. **审计与业务数据分离**：审计表只追加、不允许更新删除（可用单独 schema 或冷存）。
5. **中文检索**：P1 用"预切词 + trigram"，把分词策略记录在案，避免以后换方案时无从对照。

## 8. 对话优先的交互规范（4 条铁律）

1. **一句话必须能触发任何功能**：每个功能都有对应的"工具 + 意图示例"，且页面上任何操作都能"复制成一句命令"（`⌨` 标记的页面）。
2. **回答必须带可点开的凭证**：结论后面必须挂"报告 / 血缘图 / 口径详情 / 实例日志"的链接或卡片；**没有凭证的回答不发布**（这是我们与传统 ChatBI 最大的差别）。
3. **不确定要显式说**：置信度、解析缺口（`SELECT *` 未展开）、口径未登记、数据权限不足 —— 全部明确标注，不许"看起来像真的"。无 LLM key 时明确提示"当前为规则模式"。
4. **写操作三步不可省**：生成（草稿）→ 人工审核（留意见）→ 执行（留审计）；任何"一键落地/一键重跑"都必须能回滚或补齐。

**首屏布局**（P1）：

## 9. 路线图与里程碑

> 工作量是**粗估**（按 1 名全栈 + AI 辅助；单位"人周"），用于排期而不是承诺。

### P1 门户骨架 + 对话闭环（4~6 周）

- **范围**：F1（认证/RBAC/审计基础）、F2（对话工作台全部核心）、F3（只读血缘）、F4（只读口径）、F7（报告）、F10（系统设置基础）
- **交付物**：可登录、可对话、可点开凭证的完整闭环；四个部署单元跑起来；契约 v1 与 CI 门禁
- **验收演示**：登录 → 首屏问口径与血缘 → 点开血缘图与报告 → 血缘中心/口径中心看到同一份数据 → 审计日志里能看到刚才的操作
- **风险**：血缘图可视化工作量（若用 G6 需 3~5 天调优）

### P2 生成闭环 + 海豚只读运维（4~6 周）

- **范围**：F5（生成+审核+落地）、F6.1~F6.6（海豚纳管、实例、日志、工单）、F4.3~F4.5（口径版本与审核流）、F8、F9.3（飞书）
- **交付物**：一句话 → 生成链路 → 人审 → 落到海豚跑通；实例监控与审批式重跑
- **验收演示**：在对话里说需求 → 生成 3 个任务的链路 → 审核台通过 → 落到海豚 → 在平台里看到实例跑成功、点开日志看到我们插件输出的血缘报告段
- **风险**：生成物质量与人审体验（Diff 视图做不好，审核就变成走过场）

### P3 多调度纳管 + 语义层升格（6~8 周）

- **范围**：F6.7~F6.8（DataWorks/Airflow 适配器）、F4.6（口径冲突）、F8.3、F10.2~F10.3；旧仓库把 `knowledge`/`generate` 抽成包 → 门户可切进程内依赖（耦合方式从 A 切到 B）
- **交付物**：两个以上调度平台在同一控制台；口径库对外成为"语义层 API"
- **验收演示**：同一页看海豚与 DataWorks 的任务；生成 SQL 被口径校验（不一致时给建议）
- **风险**：DataWorks 权限与 API 可达性（客户环境可能受限）→ 适配器必须先做"只读可用"

### P4 开放与生态（持续）

- **范围**：F9.2（MCP Server）、F9.4（CLI）、F9.5（Webhook）、插件市场雏形
- **交付物**：外部 Agent（Claude Code / IDE）能通过 MCP 取我们的血缘与口径；认证为"数据智能能力提供方"
- **验收演示**：在 IDE 里问"这张表的口径是什么"，通过 MCP 拿到我们平台的回答与证据链接

**里程碑**：M1 = P1 演示通过 ｜ M2 = P2 生成闭环落地上线 ｜ M3 = 双平台纳管 ｜ M4 = MCP 对外开放

## 10. 风险与对策 / 明确不做

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 纳管写操作引发生产事故 | 高 | P1 只读；写操作走工单（申请/审批/执行/审计四段），支持"影响面快照"与二次确认；先在小项目空间试点 |
| 口径提炼误判 | 高 | LLM 只产候选；审核不可省；版本可回滚；冲突检测；审核意见进入提示词改进 |
| 血缘解析不全 | 中高 | 覆盖率指标 + 缺口清单 + 人工补录入口；不用"100% 覆盖"话术 |
| 范围失控（什么都想做） | 高 | P1 只做"窄而通"的对话闭环；每个阶段有明确"不做清单" |
| DataWorks 等平台 API 受限 | 中 | 适配器先做只读；受限时降级为"元数据导入"（CSV/离线快照） |
| LLM 成本与延迟 | 中 | 意图分类用小模型/规则、结果缓存、批量解析离线跑、可选本地模型 |
| 前端对话组件社区版停摆 | 中 | 对话 UI 与业务 UI 解耦（独立目录），必要时 1~2 人周自研替换 |
| 中文分词/检索效果 | 低中 | 预切词 + trigram + 同义词词典（已有术语库基础） |

**明确不做**（每阶段重申）：存储引擎、通用 BI 图表、元数据采集器重复建设、数据质量规则引擎、对外的多租户 SaaS（先做私有化单租户）。

## 11. 与旧仓库的契约与复用

| 复用项 | 形式 | 新平台怎么用 | 阶段 |
| --- | --- | --- | --- |
| `lineage-api`（解析/口径/报告/生成/海豚适配） | HTTP（`contracts/openapi.yaml`，16 端点） | 门户"内核客户端"调用；P3 后可切进程内 | P1 |
| `packages/lineage-core` | 纯 Python 包 | P3 进程内直接 import（可选） | P3 |
| `apps/ds-plugin`（LINEAGE / LINEAGE_DAG） | 海豚插件（留在旧仓库） | 作为"存量链路采集入口"：新平台触发解析时读它的产物 | P2 |
| 口径知识库（SQLite） | 文件/服务 | P1 通过旧仓库 API 读；P3 迁到 PG（保留 SQLite 作为离线导出） | P3 |
| 报告渲染 | HTTP | 报告中心内嵌 iframe；P3 可选前端自渲染 | P1 |
| CLI / 飞书机器人 | 命令/机器人 | 与 Web 共用 Agent 后端（同源会话） | P2 |
| 分层守卫思路 | 脚本 + 用例 | 新仓库 `tools/check_layering.py` 同款 | P1 |

**契约演进规则**：只追加字段；破坏性变更升 `/v2` 并保留旧版至少一个迭代；新平台**不 import 旧仓库内部模块**（旧仓库同理）——这样两边可以各自独立发布。
