| 项 | 内容 |
| --- | --- |
| **定位（一句话）** | 面向已建有调度平台的企业，做**对话优先的数据智能平台**：纳管调度、解析存量链路、固化业务口径、按需反向生成 SQL 与任务流 |

| **统一结果模型** | 平台所有结果（血缘/口径/Agent 回答/生成 SQL/数据字典）统一为 `{value, confidence, status, evidence[], source, version}`，`status ∈ {verified, inferred, candidate, unresolved, stale}` |

## 1. 定位与边界

### 1.1 是什么

一个**位于调度平台之上、面向"人 + Agent"的数据智能层**：
- 往下：**纳管**已有调度平台（P1 只有海豚；P4 起 DataWorks/Airflow），只读为主，写操作审批后执行
- 中间：把平台上**已经跑着的**脚本与任务流解析成**技术血缘**与**业务口径知识**（人审 + 版本）
- 往上：以**对话**为统一入口，做问数、影响分析、需求→SQL/任务流生成，并把生成物**安全落地**回调度平台

### 1.2 不是什么（防止范围失控）

| 不做 | 原因 / 替代 |
| --- | --- |
| 不重做存储与计算引擎 | 用客户已有 Hive / Doris / DWS / 湖仓 |
| 不做通用 BI 图表 | 可对接既有 BI；平台只给"可点开的凭证" |
| 不重复建设元数据采集 | 需要时对接 DataHub / OpenMetadata |
| 不重复建设数据质量规则引擎 | 海豚 3.0+ 原生数据质量、DataWorks 已覆盖；我们只做"链路质量体检" |
| 不把插件做成平台的前提 | 插件只是三个入口之一（见 §11.3） |
| P1 不做任何写操作 | 先只读建立信任 |

### 1.3 竞品关系（调研结论落地）

| 玩家 | 他们在做 | 我们的关系 |
| --- | --- | --- |
| WhaleStudio（海豚原厂） | Data Engineering Agentic Control Plane，**绑自家调度 + 商业授权** | 我们：**不绑调度 + 可私有化** |
| DataWorks / Quick BI 小Q / 析言GBI / 网易知数 | 对话入口 + 生成，**绑自家云** | 我们：可私有化、跨平台 |
| SuperSonic（腾讯开源） | Chat BI + **语义层约束 Text2SQL** | 借鉴：把我们的口径库**升格为语义层**去约束生成 |
| DataHub / OpenMetadata | 技术血缘与元数据，OpenMetadata 2.0 转向"AI Agent 上下文层" | 互补：未来可把血缘/口径推给它们，借其生态 |
| DB-GPT / DataSphereStudio | 对话框架 / 一站式门户，**缺领域闭环** | 我们填的是领域闭环 |

### 1.4 复用清单（评审必答：哪些是别人的能力）

| 能力 | 来源 | 我们只做增量 |
| --- | --- | --- |
| 调度编排/重试/补数 | DolphinScheduler / DataWorks 原生 | 统一入口 + 审批 + 审计 |
| 任务级/表级血缘 | 海豚 3.3.1+ 血缘表、DataHub/OM | **字段级血缘** + 业务口径 + 跨平台合并 |
| 登录/SSO | Casdoor（生产）| 平台侧 RBAC 与审计 |
| 对话 UI 组件 | Ant Design X / 社区 Vue 版 | 数据域专用卡片（血缘图/字段表/口径卡/报告卡/凭证卡）|
| SQL 解析 | sqlglot（已用） | 方言适配、变量渲染、置信度标注 |

## 3. 技术栈（v1.1：只留必需）

### 3.1 P1 选型（就这些）

| 层 | 选型 | 为什么 | 代价 |
| --- | --- | --- | --- |
| Web 框架 | **FastAPI**（Pydantic v2） | 类型即文档、自带 OpenAPI（服务"契约先行"）、async 适合 Agent 编排 | 管理后台类功能要自己写 |
| ORM/迁移 | **SQLAlchemy 2 + Alembic** | 迁移可控、生态成熟 | 比 SQLModel 啰嗦 |
| 数据库 | **PostgreSQL 16**（唯一） | 平台元数据（用户/会话/审计/快照）+ JSONB 存消息与快照；**同时作为血缘"事实库"** | 中文检索要额外处理（§7.3） |
| 血缘读取 | **旧仓库 API + 旧 LineageGraph** | P1 数据量（几十~几百表、几百~几千边）完全够用 | 多跳能力受限于内核实现 |
| 认证 | **生产 Casdoor(OIDC) / 开发 `AUTH_MODE=dev`** | 不做完整本地认证（用户/密码/找回/策略），避免"为了避免自研认证又自研一套认证" | dev 模式仅供开发演示 |
| 前端 | **Vue 3 + Vite + TS + Ant Design Vue** | 与既有前端资产一致 | 见 §3.3 对话组件取舍 |
| 图可视化 | **AntV G6** | 层次/力导向布局开箱可用 | 调优成本 3~5 天 |

### 3.2 延后引入（明确触发条件）

| 组件 | 什么时候才加 | 触发条件 |
| --- | --- | --- |
| **Redis + 队列（arq/Celery）** | 出现长任务/高并发/重试/定时任务时 | P2 生成任务与批量解析上线时大概率需要 |
| **Neo4j（图查询投影）** | 多跳/路径/任意深度查询变慢或表达困难时 | 表 > 数千、边 > 数万，或需要可变长路径/最短路径（P5） |
| ES / 向量库 | 中文全文检索或语义检索不够用时 | 口径库规模与语义问数上线后 |
| Celery / Kubernetes | 单机 compose 撑不住时 | 多实例与横向扩展需求出现 |

**关于 Neo4j 的更正**：v1.0 写"关系库递归 CTE 多跳会崩"，这个结论**下得太急**。PostgreSQL 原生支持 `WITH RECURSIVE`，官方文档明确用于层级结构与图关系遍历并支持环检测；在**当前数据量级**（几十/几百张表、几百/几千条边）它足够用。正确做法是：
- **PG = 系统事实库**（血缘边的事实来源）
- **Neo4j = 图查询投影**（需要复杂图算法时，从 PG/内核同步出来，可重建、可丢弃）
这样将来迁移只是"加一个投影"，不是"换事实源"。

### 3.3 前端对话组件（P1 结论：继续 Vue）

- **事实**：Ant Design X 官方目前**只有 React 版本**（官方 FAQ 明确）；Vue 侧是社区移植 `ant-design-x-vue`。
- **决定**：**继续 Vue**，但要**抽象一层自己的对话组件**，不让第三方库的类型与 API 扩散到全项目：

```
portal-web/src/features/chat/
├── ChatMessage.vue        # 消息渲染（Markdown/表格/代码，SQL 高亮）
├── ConversationList.vue   # 会话列表
├── ChatInput.vue          # 输入框（@表 #口径 / 指令 提示）
├── ToolCall.vue           # 工具调用步骤条（可展开看真实请求与耗时）
├── EvidenceCard.vue       # ★ 凭证卡片（报告/血缘图/口径详情）——我们的产品主线
└── adapters/              # UI 适配层：ant-design-x-vue 适配器 / 自研实现
```

> 换 UI 库、甚至换前端栈时，**只替换 `adapters/` 一层**；业务代码只依赖上述自有组件。

## 7. 数据模型（概念级）

### 7.1 实体与归属（P1）

| 实体 | 关键字段（概念） | 存储 | 备注 |
| --- | --- | --- | --- |
| 用户 / 角色 | 用户↔角色（管理员/数据开发/只读） | PG | 身份来自 Casdoor（生产）或 dev |
| 会话 / 消息 | 标题、角色、内容（结构化）、引用（表/口径/报告）、工具调用记录与耗时 | PG（JSONB） | 审计与回溯的载体 |
| 表 / 字段元数据 | 库表名、层、中文名、负责人 | PG（P1 可从内核读+缓存） | — |
| 血缘边（缓存/投影） | 源、目标、表达式、来源脚本+行号、置信度、解析器版本 | PG（P1 只缓存热点） | **事实源在旧内核**；P5 再做 Neo4j 投影 |
| 口径 | 名称、类型、人话公式、忠实表达式、状态、置信度、版本 | PG（P1 读内核 + 缓存） | 与字段多对多 |
| 报告 | ID、类型、来源、文件路径、大小、生成人 | PG + 文件系统 | 报告本体是文件 |
| 审计 | 操作者、动作、对象、结果、耗时、IP、时间 | PG（只追加） | 含 Agent 工具调用 |

**P2 起增加**：项目空间、调度连接（凭据密文）、工作流/任务/实例快照（含内容指纹）、口径版本与审核单、生成任务与生成物、运维工单、告警规则与事件。

### 7.2 关系速览（P1）

```
用户 ─→ 角色 ─→ 菜单可见性
会话 ─→ 消息 ─→ 引用（表/字段/口径/报告）／消息 ─→ 工具调用记录 ─→ 审计
表/字段 ─→ 口径（依赖/产出）      旧内核(18080) ─→ 血缘边 / 口径 / 报告（P1 事实源）
```

### 7.3 关键设计点

1. **PG 是事实库、Neo4j 只是投影**（v1.1 更正）：将来上 Neo4j 时从 PG/内核同步，可重建可丢弃。
2. **快照而非覆盖**（P2 起）：工作流/任务/实例存快照 + 内容指纹 → 能回答"上周三那条血缘是什么样"，也让增量解析可验证。
3. **置信度与来源必存**：所有结果都带 `source`（脚本+行号）、`version`、`confidence`、`status`（见 §7.4）。
4. **凭据只存密文**：调度连接与模型 Key 走加密列；日志/前端/插件参数一律不出现。
5. **审计只追加**：不允许更新删除（单独 schema 或冷存）。
6. **中文检索**：P1 用"预切词 + trigram"，策略记录在案，便于日后替换。
7. **图查询必须有深度上限**（v2 加）：无论是 PG `WITH RECURSIVE` 还是内核的血缘遍历，一律带 `depth <= N`（默认 5）并设超时；超出即**截断**并在结果里标 `status=unresolved`（不假装查全），热点结果落缓存。这条也是"暂时不上 Neo4j"能站得住的工程前提。

### 7.4 ★ 统一结果模型（Evidence-first，v1.1 新增）

平台所有"结论性输出"（血缘、口径、Agent 回答、生成 SQL、数据字典）统一为同一个信封：

```json
{
  "value": "产量 = 打码量 + 跳码量 − 重码量",
  "confidence": 0.93,
  "status": "verified",
  "evidence": [
    {"type": "report", "id": "rpt_20260922_a1b2c3d4", "url": "/report/rpt_20260922_a1b2c3d4"},
    {"type": "lineage_graph", "table": "ads.ads_产销存月报"},
    {"type": "metric", "id": "m_产量", "version": 3},
    {"type": "sql_source", "file": "ads/ads_产销存月报.sql", "line": 4}
  ],
  "source": "lineage-kernel@1.0.0 / sqlglot-25.x",
  "version": "metric:产量:v3"
}
```

**status 的五个取值与语义**（贯穿全平台）：

| status | 含义 | 界面行为 |
| --- | --- | --- |
| `verified` | 已人工审核/已校验 | 正常展示，可注入生成 |
| `inferred` | 由规则/LLM 推断，未经人审 | 标"推断"，不注入生成 |
| `candidate` | 待审候选 | 标"待审核"，进审核队列（P2） |
| `unresolved` | 依赖未解析（`SELECT *` 未展开、同名字段歧义） | 标"未解析"，给出补录入口 |
| `stale` | 来自快照/缓存，可能过期 | 标"可能过期（同步于 xx:xx）" |

**为什么值得单独立一节**：这一条同时解决了 4 件事 —— ① Agent 回答天然可解释（每答必有 `evidence`）；② 生成 SQL 有约束依据（只许引用 `verified`）；③ 数据字典口径统一；④ 前端只需要**一个卡片组件**渲染所有结论（`EvidenceCard`）。

## 8. 对话优先的交互规范

### 8.1 四条铁律

1. **一句话必须能触发任何功能**：每个功能都有"工具 + 意图示例"；页面上任何操作都能"复制成一句命令"。
2. **回答必须带可点开的凭证**：结论后必须挂 报告 / 血缘图 / 口径详情 / （P2 起）实例日志；**没有凭证的回答不发布**。
3. **不确定要显式说**：置信度、缺口（未解析）、未审核、权限不足、快照过期 —— 全部用 §7.4 的 `status` 明确标注。
4. **写操作三步不可省**：生成（草稿）→ 人工审核 → 执行（留审计）；任何"一键落地/一键重跑"都必须可回滚。

| **Phase 5 扩展与开放** | 规模化与生态 | **Redis/队列**、**Neo4j 图查询投影**、DataWorks/Airflow 适配器、MCP Server、飞书机器人、CLI、ES/向量检索 | 同一控制台看两种调度；IDE 通过 MCP 取到血缘与口径 |

**里程碑**：M1 = Phase 1 演示通过 ｜ M2 = Phase 2 平台闭环 ｜ M3 = Phase 3 生成可审 ｜ M4 = Phase 4 写操作上线 ｜ M5 = Phase 5 对外开放

### 9.1 P1 范围内的"不做清单"（评审要求，逐条承诺）

❌ Redis / arq ｜ ❌ Neo4j ｜ ❌ scheduler-adapter ｜ ❌ DataWorks / Airflow ｜ ❌ 生成与落地（apply）｜ ❌ 复杂审批流 ｜ ❌ 告警系统 ｜ ❌ 完整本地认证（用户/密码/找回/策略）｜ ❌ 会话分享与搜索 ｜ ❌ 多租户数据隔离（P2）｜ ❌ 语义检索/向量库 ｜ ❌ K8s/Prometheus

## 11. 旧仓库的处理（v1.1 重点）

### 11.1 定位改为 Data Intelligence Kernel

`sql-lineage-mvp` 不再是"SQL 血缘 MVP"，而是**数据智能内核**，保留并继续维护：
SQL Parser（sqlglot）· 血缘引擎（表级/字段级）· 工作流血缘 · 口径知识 · 生成（L1~L4）· 反向校验 · HTML 报告 · DolphinScheduler 集成与插件 · 450 个用例与门禁。

**本期对旧仓库只做三件事**：① 推送（Phase 0）；② 打 tag；③ 保持不动。内部重构（抽 `lineage-core`/`lineage-knowledge`/`lineage-generate` 包）推迟到 Phase 5 之后。

### 11.2 插件做薄（Thin Plugin）——对"插件"最重要的决定

插件今后**只负责**：

```
DolphinScheduler（TaskExecutionContext）
        ↓ 取上下文（projectCode / processDefineCode / 任务类型）
        ↓ 调 DIP / lineage 平台 API（业务逻辑全在服务端）
        ↓ 在任务日志里显示**摘要**（若干行）
        ↓ 给一个**报告 URL**
```

插件**不再负责**：SQL 解析、业务口径逻辑、Agent、图计算、大段报告渲染、权限、审批、复杂业务状态。

理由：这些能力都在服务端，放进插件等于每个海豚版本都要重新搬一遍；插件越薄，`DS 3.2 → 3.3 → 4.x` 的适配成本越低。
（现状说明：现在的插件已经是"哑客户端 + HTTP 调用服务端"，但日志渲染较重；**做薄**是后续渐进动作，不阻塞平台建设。）

### 11.3 新平台不依赖插件：三个入口并列

```
        ┌─ ① DolphinScheduler 插件（任务内触发，实时）
DS ─────┼─ ② OpenAPI 适配器（平台侧拉取，批量/定时）      →  DIP Platform
        └─ ③ 离线导入（脚本/元数据快照，受限环境兜底）
```

插件**只是三个入口之一**，不是平台的前提。这样以后接 Airflow / DataWorks 时架构依然成立。

### 11.4 与旧仓库的契约

| 复用项 | 形式 | 新平台怎么用 | 阶段 |
| --- | --- | --- | --- |
| `lineage-api`（解析/血缘/口径/报告/生成） | HTTP（`contracts/openapi.yaml`，17 端点，含漂移门禁） | `integrations/lineage-client` 调用 | P1 |
| 报告渲染 | HTTP | 报告中心 iframe 内嵌 | P1 |
| 口径知识库（SQLite） | 经内核 API 读 | P1 只读 + 缓存；迁 PG 推迟 | P1/P5 |
| 生成能力（P7） | 经内核 API | Phase 3 用；**不 apply** | P3 |
| 海豚插件 | 旧仓库（海豚生态件） | 作为入口①：产物（报告/血缘）供平台读取 | P2+ |
| 分层守卫思路 | 脚本+用例 | 新仓库同款 `tools/check_layering.py` | P1 |

**契约演进规则**：只追加字段；破坏性变更升 `/v2` 并保留一个迭代；**双仓库互不 import 内部模块**。
